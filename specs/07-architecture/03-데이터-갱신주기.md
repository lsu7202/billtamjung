# 데이터 갱신 주기 · 절차 (정본)

> master(부동산 원천) 데이터의 **소스별 확정 갱신 주기**와 **실제 업데이트 절차**. app(유저) 데이터는 API가 실시간 처리라 대상 아님.
> 스케줄러 **설계**는 [[01-상세설계]] §2, 스왑 메커니즘도 §2.6·§2.8. 이 문서는 그 위에 **주기 확정 + 현행(수동) 운영 절차**를 얹는다. 작성 2026-08-02.

---

## 0-A. 2026-09-07 — 주기별 실행이 실물이 됐다

주기가 **문서에만 있던 값에서 코드가 읽는 값**이 됐다. 선언은 `pipeline/units.py` 의 `cadence` 칸이고,
`scripts/run_unit.py --cadence weekly` 가 그 주기의 단위와 뒤따르는 파생만 돌린다.

| 주기 | 단위 | 부르는 법 |
|---|---|---|
| 주 | `news.notice` `news.press` `news.g2b` | `--cadence weekly` |
| 월 | `news.facility` `stores.localdata` `sales` `land_adjust` | `--cadence monthly` |
| 분기 | `news.permit` `stores.sbiz` `elevator` `rent_index` `ledger` | `--cadence quarterly` |
| 반기 | `news.zones` | `--cadence semiannual` |
| 연(5월 말) | `gongsi` | `--unit gongsi` |

**아직 안 뗀 것 둘**: `parcels`(반기) 는 공간 조인·부속지번·SQLite 넷에 걸려 있고,
`transit`(반기) 은 자기 표 없이 `buildings` 의 칸이다. 둘 다 지금은 `ledger` 안에서 같이 돈다.

**스케줄러는 여전히 안 붙였다**(기존 결정). 단위가 가벼워졌으니 손으로 부르는 것으로 충분하다.
자동 크롤을 붙일지는 미정 — 지금은 `--no-crawl` 로 받기를 끄고 이미 받은 파일로 도는 일이 많다.

## 0. 현재 상태 — ⚠️ 자동화는 "설계"만, 운영은 **수동**

| | 상태 |
|---|---|
| loader 스왑 로직(`pipeline/loader.py`) — 검증게이트·advisory lock·뷰 재지정·version++·감사로그 | ✅ **구현·동작** (수동 CLI) |
| `_v1` 물리테이블 + 뷰 + `master_version`/`master_loads` (mig 0002/0007/0009) | ✅ 구현 |
| Cloud Scheduler/Job **자동 트리거** | ❌ **미배포** — Terraform `bt-load-rtms` 골격 1건뿐, 타깃 엔드포인트(`worker /jobs/load`) 부재 |
| pipeline/loader 컨테이너 이미지 | ❌ 없음(`backend/Dockerfile`은 api/worker만) |

즉 **아래 "주기"는 지금은 코드가 강제하는 게 아니라 운영 약속(target)**이다. 실제 갱신은 §3 수동 절차로 사람이 실행한다. 자동화 배포에 필요한 선행조건은 §5.

## 1. 확정 갱신 주기 — 원천 소스 (loader 테이블 단위)

loader는 **테이블 단위**로 스왑한다(원본 파일 단위 아님). 한 테이블이 여러 원본을 합치므로, 그 테이블의 주기 = **가장 빨리 바뀌는 입력** 기준.

| loader 테이블 | 합쳐지는 원본 | 확정 주기 | 크론(Asia/Seoul) | 주기 근거(원본 발표) |
|---|---|---|---|---|
| `gongsi_series` (공시지가 시계열) | 개별공시지가 연도판(V-World AL_D150) | **연 1회 · 5월 말** | `0 3 25 5 *` | 개별공시지가 5.31 결정·공시 |
| `buildings` (건물) | 건축HUB 표제부/총괄/층별개요/대수선(djy·kcy) + 엘리베이터(승강기공단) + 교통(지하철·버스) + 좌표(연속지적도) | **분기** | `0 4 1 1,4,7,10 *` | 건축HUB 마트 갱신 주기 |
| `floor_outline` (층별개요) | 건축HUB `djy_04` | **분기**(건물과 동반) | 〃 | 〃 |
| `parcels` · `building_parcels` (필지) | 토지특성(V-World AL_D194) + 용도지역(UQ111) + 개발제한(UD801) + 규제 7종 SHP + 법정건폐/용적 + 부속지번 | **반기** | `0 4 1 3,9 *` | 도시계획 고시(수시→반기 스캔) · 토지특성/공시지가 최신값은 연 1회 |

## 3. 파생 의존 순서 (DAG) — 무엇 먼저 → 무엇 계산

```
[연1회 5월]  gongsi_series ─┐
[분기]       buildings, floor_outline ─┬─▶ build_floor/build_bldg → floor_rent_est, building_rent_est
             sanggwon_rent_series(통계표) ┘
[반기]       parcels, building_parcels (용도지역·규제·토지특성)
[매월 1일]   sales_history ─┬─▶ build_income_cap → income_cap
             land_adjust(지가변동률) ┘         │
                                                ▼
             building_rent_est + income_cap + land_adjust + sales_history + gongsi
                                                ▼
                              build_sale_est → building_sale_est  (빌탐정 적정가)
```

- **월 체인**: 실거래 → income_cap → (land_adjust) → **적정가**. 매물 적정가를 매월 최신 실거래로 갱신.
- **분기 체인**: 건물·층별 → 임대추정. (임대는 통계표 기반이라 천천히 변함)
- **연 체인**: 공시지가 시계열·토지특성.
- 순서 위반 시: `income_cap`·`building_sale_est`는 `building_rent_est` 없으면 빈 조인. `build_sale_est`는 `income_cap`·`land_adjust`(=`ref.formula_params` time_adjust) 없으면 서울 폴백/부정확.

## 4. 업데이트 실행 절차 (현행 = 수동)

한 소스를 갱신하려면(예: 실거래 월간):

1. **원본 수집** — 소스별 방법:
   - 실거래: `data/tools/download_rtms.sh` (rt.molit.go.kr 스크레이핑, 인증키 불요)
   - 공시지가/토지특성/용도지역/규제: V-World·NSDI에서 SHP/DBF 내려받아 `data/raw/…` 배치
   - 건축물대장: 건축HUB 마트 텍스트(`mart_djy_*`,`mart_kcy_*`) 배치
   - 교통: 서울 열린데이터광장 JSON 배치
2. **중간 빌더** — `data/tools/build_*.py`로 원본 → `_*.jsonl`/`_*.json` 중간산출 (필요 시 `build_sqlite.py` → `data/빌탐정.db`)
3. **CSV export** — `pipeline/export_seoul.py`·`export_parcels.py`·`export_series.py` → loader용 CSV
4. **적재(스왑)** — `DATABASE_URL=… python pipeline/loader.py --source <buildings|parcels|building_parcels|gongsi_series|sales_history> --csv <path>`
   - loader가 자동: staging COPY → **검증게이트(행수≥95%·NOT NULL·ST_IsValid·서울 bbox·PK유니크)** → 통과 시 **뷰 재지정 원자 스왑 + version++**, 실패 시 스왑 안 함(기존 유지)
5. **파생 배치** — 원천 스왑 후 §3 순서로 `scripts/rent_estimate/build_*.py` 실행(주기 해당분만). 예: 실거래 갱신 → `build_income_cap` → `build_sale_est`
6. **라이브 패치 재실행** — `scripts/elevator/fill_elevator.py` 등(buildings 재스왑 시)

**멱등·안전장치**: loader는 advisory lock으로 단일 실행, staging TRUNCATE 후 COPY라 재시도 무해. 검증 실패 시 서비스 데이터 무변경. 스왑 커밋 순간 `master_version.loaded_at` 갱신 → 기존 보고서 "데이터 변경됨" 표시.

## 5. 자동화(스케줄러) 배포에 필요한 선행조건

§1·§2 주기를 실제 크론으로 돌리려면 3가지가 선행돼야 한다(현재 전부 미구현):

1. **컨테이너화** — `pipeline/`·`scripts/`·`data/tools/`를 담은 Cloud Run **Job 이미지**(현 Dockerfile은 api/worker만).
2. **적재 트리거** — worker `/jobs/load` 엔드포인트 **또는** loader용 Cloud Run Job 배포 + pipeline→loader 체이닝.
3. **Terraform 스케줄러 확장** — 현 `bt-load-rtms` 골격 → §1·§2 소스별 Scheduler(연1회·분기·반기·매월 + 파생 후속)로 확장, GCS 산출물 보존·실패 알림(Sentry/메일) 연결.

그 전까지 갱신 주기는 **운영 약속**이며 §4 절차로 사람이 집행한다.
