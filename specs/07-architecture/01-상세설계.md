## 0. NoSQL 쓸 것인가? — **결론: 베타는 Postgres 단일. NoSQL 보류.**

| 후보 | 판단 |
|---|---|
| **Cloud SQL (PostgreSQL + PostGIS)** | ✅ **단일 주력.** 크레딧 원장=ACID 필수 · 공간검색=PostGIS · 오버레이/위키 유연필드=JSONB · 조인·집계 다수 |
| Firestore (문서·실시간) | ⏸ **정식 후보**: 알림 팬아웃·실시간 팀 협업(프레즌스)·디바이스 세션. 지금은 불필요 |
| Bigtable (와이드컬럼) | ❌ 초대용량 시계열용. 우리 규모 과함 |
| Memorystore (Redis) | ❌ 캐시·큐 → 이미 폐기(Cloud Tasks + Postgres로 충분) |

**근거**: (1) 크레딧 차감은 트랜잭션 정합이 생명 → 관계형 필수. (2) 우리 데이터는 관계·공간 중심이라 문서DB 이점이 없다. (3) 유연 필드(오버레이·위키·업무)는 **JSONB 컬럼**으로 흡수 → 스키마 유연성은 Postgres 안에서 확보. (4) 100명에 이종 DB 2개는 운영·정합 부채만 늘림.
→ **하나의 Cloud SQL, master·app 2스키마**([[00-system-architecture]] §2). NoSQL은 정식에서 알림·실시간이 실제로 필요해질 때 Firestore로 국소 도입.

## 1. 백엔드 구조 (FastAPI)

### 1.1 레이어드 + 도메인 모듈
```
backend/app/
  main.py               # FastAPI 앱(api). 미들웨어·라우터 등록
  worker.py             # 워커 엔트리(Cloud Tasks 핸들러 전용 앱)
  core/
    config.py           # 환경설정(Secret Manager 주입)
    db.py               # 커넥션 풀(asyncpg), 세션 의존성
    security.py         # JWT 발급/검증, 비번 해시(argon2)
    deps.py             # get_current_user, get_team_scope
    errors.py           # 공통 예외 → HTTP 매핑
  domains/
    auth/               # 가입·로그인·refresh (router·service)
    accounts/           # 프로필·계정설정·삭제
    teams/              # 팀·멤버·초대·권한·공유범위
    search/             # 통합검색·자동완성·영역(폴리곤)검색
    buildings/          # master 조회 + overlay 병합(§DB merge)
    overlays/           # 필드 수정·되돌리기(자동저장)
    listings/           # 매물 등록/선점(담당자)
    market/             # S03 주변시세(PostGIS comps)
    wiki/               # 집단지성 특이사항
    reports/            # 보고서 생성 요청·조회 / 워커 잡
    credits/            # 잔액·원장·차감
  jobs/
    generate_report.py  # 워커 잡: 조립→가치점수/적정매매가→python-pptx→GCS
```
- **레이어**: `router`(검증·직렬화) → `service`(비즈니스·트랜잭션) → `repository`(SQL). 순환 없음.
- **DB 접근**: **asyncpg 풀 + SQL 우선**(PostGIS·오버레이 병합·집계는 raw SQL이 명확). 마이그레이션은 **Alembic**(스키마 버전). ORM 과의존 지양(복잡 쿼리 가독성).
- **api ↔ worker**: 같은 코드베이스·다른 엔트리(`main.py`/`worker.py`). 워커는 Cloud Tasks OIDC만 수신, 외부 비노출([[00-system-architecture]] §5).
- **검증**: Pydantic v2 모델(요청/응답). 응답에서 민감필드(전화)는 스코프 기반 마스킹.

### 1.2 요청 파이프라인(공통)
```
요청 → CORS(불필요, 동일오리진) → JWT 미들웨어(access 검증 → user·team_id 주입)
     → 라우터(Pydantic 검증) → 서비스(트랜잭션 경계) → 리포지토리(SQL) → 응답(마스킹)
```
- `team_id`는 **토큰 클레임에서만** 도출(요청 파라미터 무시) → 팀 격리 강제.
- 트랜잭션 경계 = 서비스 함수 1개 = DB 트랜잭션 1개(크레딧 차감처럼 원자성 필요한 것 포함).

## 2. 데이터 업데이트 스케쥴러 (master 적재) — **베타부터 완전 자동**(A-5 확정)

> master(부동산 원천) 데이터 전용. app(유저) 데이터는 API가 실시간 처리라 무관.
> 신선도 판정([[S0M-마이페이지]] `데이터 변경됨`)의 근간이므로 베타에서 완성한다.

### 2.1 파이프라인 → 프로덕션 (자동)
```
[Cloud Scheduler] ── cron ──▶ [Cloud Run Job: pipeline]   수집·정제 → CSV
   소스별 스케줄                       │
                                        ▼   (Job 종료 후에도 산출물 보존)
                                  [GCS] raw/{source}/{run_id}/*.csv
                                        ▼
                        [Cloud Run Job: loader]  ── COPY ──▶ Cloud SQL: master_staging
                                        ▼
                             검증 게이트(§2.5) 통과?
                          ┌───────────┴───────────┐
                        통과                      실패
                          ▼                        ▼
              원자 스왑(§2.6) + version++     스왑 안 함(기존 유지) + 알림(§2.7)
```
- **파이프라인 Job**: 기존 로컬 23스크립트를 컨테이너화(`pipeline/` §7). Scheduler가 트리거. 산출 CSV는 GCS에 `run_id`별로 남긴다(재현·롤백 근거).
- **loader Job**: pipeline 성공 후 실행(체이닝: pipeline 마지막 스텝이 loader Job을 `execute`, 또는 pipeline 완료를 트리거로 loader Scheduler). CSV → `master_staging` COPY → 검증 → 스왑.
- **Cloud Run Job**(≠ Service): 실행 후 종료, 유휴 비용 0. 스케줄·수동 트리거로만 깨어남.

### 2.2 소스별 크론 스케줄
| 소스 | 주기 | 크론(Asia/Seoul) |
|---|---|---|
| 공시지가 | 연 1회(5월 말) | `0 3 25 5 *` |
| 실거래·매각(RTMS) | 매월 | `0 3 1 * *` |
| 건축물대장·토지 | 분기 | `0 4 1 1,4,7,10 *` |
| 교통·상권 | 반기 | `0 4 1 3,9 *` |
- 스케줄은 **소스별 독립**(한 소스 실패가 다른 소스 적재를 막지 않음). 새벽(저트래픽) 실행.
- **수동 트리거**도 항상 가능: `gcloud run jobs execute loader --args=...`(임시 보정·재적재).

### 2.3 멱등성 · 재실행 안전
- loader는 **멱등**: 시작 시 `master_staging` **TRUNCATE 후 COPY**(중복 없음). Job 재시도해도 결과 동일.
- **동시 실행 방지**: Postgres **advisory lock**(`pg_try_advisory_lock`)으로 loader 단일 실행 보장. 이미 돌면 즉시 종료.
- Cloud Tasks/Job 재시도 = **0~1회**로 제한(중복 스왑 방지).

### 2.4 적재 감사 로그
```
master_loads (audit)
  run_id · source · started_at · finished_at · status(running|success|failed)
  rows_in · rows_out · validation(jsonb) · from_version · to_version · error?
```
- 매 실행 1행. 마지막 성공 버전·시각을 여기서 조회 → 관측·롤백 근거.

### 2.5 검증 게이트 (스왑 전 필수 통과)
스왑은 **검증 통과 시에만**. 하나라도 실패하면 기존 데이터 유지 + 알림.
- **행 수 하한**: `rows_staging ≥ rows_live × 0.95` (급감=수집 오류 의심 → 차단). 상한도 경보(비정상 급증).
- **필수 NOT NULL**: PK·좌표(geom)·용도지역 등 핵심 컬럼 NULL 0건.
- **공간 유효성**: `ST_IsValid(geom)` 전건 통과(또는 `ST_MakeValid` 보정 후 재검).
- **범위·형식**: 공시지가>0, 면적>0, 연도 범위, 좌표 서울 bbox 내.
- **참조 정합**: 필지↔건물 대표지번 매핑 고아 0건(허용 오차 내).
- **중복**: PK 유니크.
- 결과는 `master_loads.validation`(jsonb)에 항목별 pass/fail 기록.

### 2.6 무중단 스왑 방식 (결정: **뷰 재지정**)
- master 테이블은 **버전 물리테이블 + 뷰**: 실체 `master.buildings_v{n}`, 서비스는 뷰 `master.buildings`가 최신 버전을 가리킴.
- 스왑 = **`CREATE OR REPLACE VIEW`로 새 버전 지정**(단일 트랜잭션, 즉시·무락). 읽는 쪽은 트랜잭션 경계에서 구/신을 일관되게 봄(MVCC).
- 구버전 테이블은 **1세대 보존 후 삭제**(롤백 여지). 
- *대안(더 단순)*: 신테이블 적재 후 `ALTER ... RENAME` swap — 짧은 ACCESS EXCLUSIVE 락. 새벽·100명이면 허용. **베타 기본은 뷰 재지정**(무락).

### 2.7 실패 · 알림 · 롤백
- **파이프라인 실패**(수집 오류): loader 미실행, 기존 데이터 유지. 알림.
- **검증 실패**: 스왑 중단, `master_loads.status=failed`+사유. 기존 유지. 알림.
- **알림 경로**: Cloud Logging 로그기반 알림 + **Sentry/이메일**(무료 티어). "master 적재 실패({source})" 즉시 통지.
- **롤백**: 뷰를 직전 버전으로 재지정(1줄) → 즉시 복구.

### 2.8 스왑 트랜잭션 안에서 버전·신선도 갱신
```
BEGIN;
  CREATE OR REPLACE VIEW master.buildings AS SELECT * FROM master.buildings_v{n+1};  -- (+ 관련 뷰)
  UPDATE master.master_version SET version = {n+1}, loaded_at = now(), source = :source;
COMMIT;
```
- 이 커밋 순간 `master_version.loaded_at`이 갱신 → 이후 기존 보고서는 **`데이터 변경됨`**([[S0M-마이페이지]] §3.2a). 스케쥴러 ↔ 신선도(§4)가 원자적으로 연결.

## 3. DB 구조 — 스키마 · 함수 · 트리거

### 3.1 스키마 분리
- **`master`** (읽기전용, 파이프라인만 씀): buildings·parcels·gongsi_series·sales·transit·regulations. 앱은 SELECT만.
- **`app`** (RW, API): accounts·teams·team_members·listings·overlays·floor_rents·wiki_*·ad_prices·memos·favorites·reports·credit_entries·saved_searches. (스키마 정본 = [[../04-data/schema-app]])

### 3.2 핵심 트리거
```sql
-- (1) updated_at 자동 — 신선도 판정의 원천
CREATE OR REPLACE FUNCTION app.set_updated_at() RETURNS trigger AS $$
BEGIN NEW.updated_at := now(); RETURN NEW; END $$ LANGUAGE plpgsql;
-- 모든 app 편집 테이블(overlays·listings·floor_rents·ad_prices…)에 BEFORE UPDATE 부착

-- (2) 크레딧 원장 → 잔액 캐시 동기화 (append-only 원장, 잔액은 캐시 테이블)
CREATE OR REPLACE FUNCTION app.apply_credit_entry() RETURNS trigger AS $$
BEGIN
  INSERT INTO app.credit_balances(user_id, bucket, amount)
  VALUES (NEW.user_id, NEW.bucket, NEW.delta)
  ON CONFLICT (user_id, bucket)
  DO UPDATE SET amount = app.credit_balances.amount + NEW.delta;
  RETURN NEW;
END $$ LANGUAGE plpgsql;
CREATE TRIGGER trg_credit AFTER INSERT ON app.credit_entries
  FOR EACH ROW EXECUTE FUNCTION app.apply_credit_entry();
```
- 원장(`credit_entries`)은 **append-only**(수정·삭제 금지) → 감사 가능. 잔액은 버킷별 캐시(`credit_balances`)로 O(1) 조회.

### 3.3 핵심 함수
```sql
-- 화면값 병합: master + app.overlays COALESCE (팀 스코프)
app.building_view(p_pk bigint, p_team_id bigint) RETURNS jsonb
  -- master.buildings/parcels/시계열 + LEFT JOIN app.overlays(team_id, target)
  -- 필드별 COALESCE(overlay.value, master.value)

-- 영역(폴리곤) 검색: ST_Within
app.search_polygon(p_geojson jsonb, p_filters jsonb) RETURNS setof ...
  -- WHERE ST_Within(b.geom, ST_MakeValid(ST_GeomFromGeoJSON(p_geojson))) AND <filters>

-- 주변 comps: ST_DWithin (S03)
app.nearby_comps(p_lat, p_lng, p_radius_m, p_floor_range) RETURNS ...

-- 크레딧 차감(트랜잭션 내 호출): 만료 임박 버킷부터 소진
app.deduct_credit(p_user bigint, p_amount int, p_ref uuid) RETURNS void
  -- 소진 순서: 월지급(월말 소멸) → 이월 → 충전. 각 버킷 credit_entries에 음수 delta 기록
```

### 3.4 제약·인덱스
- **선점(배타)**: `CREATE UNIQUE INDEX ON app.listings(building_pk, team_id) WHERE assignee_id IS NOT NULL;` → 팀 내 1매물=1담당자 DB 강제.
- **공간**: `GIST(geom)` on master.buildings·parcels(영역·반경 검색).
- **자동완성**: 주소 컬럼 `text_pattern_ops`(접두검색) + `pg_trgm GIN`(유사도).
- **스코프**: `(team_id, building_pk)` btree(사적 레이어 조회).
- **크레딧 무결성(정식)**: 잔액 CHECK(≥0)는 정식 전환 시 추가(베타는 그림자 계량 → 미적용).

## 4. 크레딧 차감 구조

### 4.1 데이터 모델
```
credit_entries (원장, append-only)
  id · user_id · delta(±) · bucket(monthly|carryover|topup|reward)
  reason(report_analysis|report_briefing|wiki_reward|monthly_grant|carryover|topup)
  ref_id(report_id 등) · created_at · expires_at(monthly만 월말)
credit_balances (캐시, 트리거 동기화)
  user_id · bucket · amount   (PK: user_id,bucket)
```
- **잔액** = Σ balances(미만료). 화면 표기 = 월지급 잔여 + 이월(+ 충전).

### 4.2 차감 흐름 (보고서 생성)
```
worker: 보고서 생성 성공 → 같은 트랜잭션 안에서
  app.deduct_credit(user, 30, report_id)   -- 분석 30 / 브리핑 10
    소진 순서: monthly(소멸 임박) → carryover → topup
  reports.status='완료', source_watermark 기록  (§신선도)
실패 → 롤백 → 크레딧 미차감([[R-보고서]] §7)
```
- **성공 시점 차감**(홀드·예약 없음) — 실패해도 원장에 흔적 없음.
- **그림자 계량(베타)**: `BILLING_ENFORCED=false` → 잔액 음수 허용, 원장엔 기록(사용 패턴 관측). 정식에서 플래그 on + 잔액 CHECK.

### 4.3 월 주기 배치 (Cloud Scheduler)
```
월초: 각 구독자에 monthly_grant(+플랜별) 원장 기록, expires_at=이달 말
월말: 미사용 monthly 잔액 → expire 원장(−) 기록(소멸). 이월 정책은 플랜별
```
- 위키 기여 채택 → `reward`(+3) 원장. 충전(정식) → `topup`(무기한).

## 5. 회원 · 계정 · 팀 구조

### 5.1 테이블
```
accounts   id · email(uniq) · password_hash(argon2) · name · office_name?
           phone(정식·암호화) · tier(trial|starter|pro) · terms_agreed_at · created_at
teams      id · name · owner_id · created_at
team_members  team_id · user_id · role(owner|member) · status(active|invited) · joined_at
```
- **가입 트랜잭션(원자)**: accounts INSERT → teams INSERT(1인, name=office_name or `{name} 팀`) → team_members INSERT(owner, active) → credit_entries(trial +60). → `team_id` 항상 존재(마이그레이션 0).
- **팀 격리**: 모든 사적 레이어에 `team_id NOT NULL FK`. 조회는 토큰의 team_id로 스코프.
- **선점**: listings.assignee_id + 부분 UNIQUE(§3.4). 재배정·승계는 서비스 로직(정식).

### 5.2 인증 토큰
- **access JWT**(~30분): sub(user_id)·team_id·role·tier. Authorization 헤더.
- **refresh**(~30일, httpOnly·Secure·SameSite=Lax 쿠키, 회전): `/auth/refresh`로 재발급. 로그아웃=refresh 폐기.
- 전화 인증(SMS)·소셜 = 정식([[../03-features/S00-로그인]] §3.3.1/§3.4).

## 6. 프론트 구조 (React SPA)

### 6.1 스택·구성

## 8. HTTPS / TLS 전략

**원칙: 인증서는 전부 Google-managed(자동 발급·자동 갱신). 수동 인증서·갱신 없음. 전 구간 암호화.**

### 8.1 구간별 TLS
```
[브라우저] ──HTTPS──▶ [Firebase Hosting]  (Google-managed 인증서, 자동 갱신)
                          │  정적 프론트 서빙 + rewrite
                          └──HTTPS──▶ [Cloud Run: api]  (*.run.app 기본 TLS)
[Cloud Tasks] ──HTTPS(OIDC)──▶ [Cloud Run: worker]
[Cloud Run] ──TLS──▶ [Cloud SQL] (Cloud SQL Connector, IAM+TLS)
[Cloud Run] ──TLS──▶ [Secret Manager · GCS · 네이버 API]
```
- **같은 오리진 전략의 이점**: 클라이언트는 **프론트 도메인(HTTPS) 하나로만** 통신하고, `/api/**`는 Firebase가 Cloud Run으로 프록시(§[[00-system-architecture]] §5) → API가 프론트 인증서 아래로 들어와 **별도 api 도메인·인증서 불필요**, CORS도 없음.
- Cloud Run·Cloud SQL·Tasks·Secret·GCS 간 내부 호출도 전부 TLS → **평문 구간 없음**.

### 8.2 도메인 · 인증서
| 단계 | 도메인 | 인증서 |
|---|---|---|
| **베타 초기** | `빌탐정.web.app`(Firebase 기본) | Firebase 자동 HTTPS (설정 0) |
| **베타/정식** | 커스텀 도메인(예: `app.billtamjung.co.kr`) | Firebase 커스텀 도메인 → Google-managed cert 자동 발급 |
- Cloud Run에 커스텀 api 도메인이 필요하면(rewrite 안 쓸 경우) **Cloud Run domain mapping**으로 역시 Google-managed cert. **단 rewrite 전략에선 불필요.**

### 8.3 강제·헤더 (HTTPS 강화)
- **HTTP→HTTPS 강제 리다이렉트**: Firebase Hosting 기본 동작(자동).
- **HSTS**: `Strict-Transport-Security: max-age=31536000; includeSubDomains`. `preload`는 **인증서·도메인 안정 확인 후**(되돌리기 어려움) 켠다.
- **보안 헤더**(Firebase `hosting.headers` + api 미들웨어): `Content-Security-Policy`(네이버 지도·GCS 서명URL 화이트리스트), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`.
- **쿠키**: refresh 토큰 = `Secure`(HTTPS 전용) + `HttpOnly` + `SameSite=Lax`. HTTPS 전제라야 성립(§5.2).

### 8.4 프로비저닝 순서 · 로컬
1. 도메인 확보 → DNS(Cloud DNS 또는 등록기관) A/AAAA·TXT 검증 레코드.
2. Firebase Hosting에 커스텀 도메인 연결 → **Google 자동 인증서 발급**(수분~최대 24h).
3. 발급 확인 후 HSTS on → 안정화 후 `preload` 등록(선택).
4. 네이버 `ncpKeyId` **HTTPS 도메인 등록**(지도 SDK 허용 도메인).
- **로컬 개발**: `localhost`는 http 허용(또는 `mkcert`로 로컬 HTTPS). `Secure` 쿠키는 dev 환경에서 완화 플래그.

### 8.5 단계
- 🟢 **베타**: Firebase 기본 HTTPS(`*.web.app`)로 즉시 확보 — TLS 작업 사실상 0. HSTS·보안헤더 적용.
- 🔵 **정식**: 커스텀 도메인 + Google-managed cert + HSTS preload + CSP 정교화.

## 9. 유지보수성 · 확장성 — "데이터 추가·수정이 쉬운가?"

목표: **필드/소스/enum/산식을 추가·수정할 때 고치는 곳을 1곳으로 수렴.**

### 9.1 현재 유리한 구조 (유지)
- **오버레이 = EAV**(`overlays.field`): 유저 수정 가능 **사적 필드 추가 = 스키마 변경 0**. 새 `field` 키만.
- **버전 물리테이블 + 뷰**(§2.6): master 스키마 진화가 과거 스냅샷·보고서를 안 깨뜨림.
- **저장 코드 ↔ 표시 라벨 분리**(`enums.md`): 라벨 변경이 저장·로직에 무영향.
- **단일 출처 문서**: 필드=`data-overview.md` · 산식=`formulas.md` · enum=`enums.md`.

### 9.2 취약점 → 개선 (착수 원칙)
| 변경 시나리오 | 현재 | 개선안 → 고칠 곳 |
|---|---|---|
| **새 master 공공 필드** | 파이프라인·컬럼·뷰·병합·API·UI 5~6곳 | **필드 레지스트리(메타데이터 주도)** → 레지스트리 1곳 + (master면) 컬럼 1개. UI·API는 메타로 자동 |
| **새 데이터 소스** | 스크립트·loader·cron 추가 | 모듈형 파이프라인(`sources/transforms/loaders`) — 새 모듈 + Scheduler 1줄. 이미 확장 용이 |
| **enum 값 추가** | 코드 하드코딩이면 배포 | **`ref_enums` 테이블화** → INSERT(배포 0) |
| **산식 파라미터 튜닝**(가중치·시점보정·등급컷) | 코드 상수면 배포 | **`ref_formula_params`(버전) 테이블화** → 데이터 수정(코드 불변). `formulas.md`=정의, 값=데이터 |
| **사적 필드 추가** | overlays EAV | 이미 스키마 0 ✅ |

### 9.3 핵심: 필드 레지스트리(메타데이터 주도)
`data-overview.md`(컬럼정의서)를 **기계가 읽는 정본**(YAML/JSON 또는 `ref_fields` 테이블)으로 승격:
```
field_key · label · unit · type(num|text|enum|date|series) · layer(공공|사적|파생)
  · source(파일·컬럼) · enum_ref? · formula_id? · editable? · masked?
```
- **파이프라인**: 레지스트리로 CSV↔컬럼 매핑 생성.
- **API**: 응답 직렬화·마스킹을 레지스트리로 구동(새 필드 자동 노출, 옵트인).
- **프론트**: 필드 컴포넌트가 메타(label·unit·type)로 **자동 렌더** → 화면마다 하드코딩 안 함.
- 효과: **새 필드 = 레지스트리 1곳 수정**(+ master면 물리컬럼). enum·산식은 데이터라 **배포 없이** 수정.
- **실제 DDL 확정**: [[../04-data/schema-ref]](`ref.fields`·`ref.enums`·`ref.formula_params` + 오버레이 검증 트리거 + 시드).

### 9.4 스키마 변경 규율
- **app**: Alembic 마이그레이션(리뷰·롤백). EAV라 필드 추가엔 대개 불필요.
- **master**: 버전 물리테이블 + 레지스트리 diff. 컬럼 추가는 하위호환(누락=결측 처리, §7 `—`).
- **파괴적 변경**(필드명/타입): 버전테이블 덕에 과거 보고서 안전, 신버전부터 적용.

> 결론: **사적 데이터·소스 추가는 지금도 쉬움.** **공공 필드·enum·산식**만 지금은 다층/배포 의존인데, **필드 레지스트리 + enum·산식 데이터화**를 착수 시 채택하면 "한 곳만 고치면 되는" 형태가 된다. 베타에서 레지스트리 뼈대만 잡아두면 이후 확장 비용이 급감.
