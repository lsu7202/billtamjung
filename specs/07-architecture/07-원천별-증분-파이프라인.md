# 원천별 증분 파이프라인 — 계획 (2026-09-06)

> 대표 지적: 「파이프라인이 항상 전체 빌드를 해야 해서 문제다. 데이터별로 갱신 주기가 있으니
> 빌더도 개별로 돌게 버전 관리를 해야 한다. 소식은 주기가 제각각이라 더 세분화해야 한다.」

## 1. 지금 무엇이 문제인가

`run_pipeline.sh` 는 단계가 넷(crawl → activate → build → load → derive)이고 **어느 원천이 바뀌었든 통째로 돈다.**

| 단계 | 지금 | 비용 |
|---|---|---|
| build (`pipeline/build_all.py`) | 28단계 전부. 공간 조인부터 SQLite 통합, CSV 내보내기까지 | 수 시간 · **디스크 25GB**(HUB 압축본 637MB 를 11GB 로 펴고, 중간 jsonl·SQLite·CSV 가 겹친다) |
| load (`pipeline/loader.py`) | 표 12개 전부 세대 스왑 | 30분 |
| derive | 파생 20단계 전부(임대추정 18분·건물추정 15분 포함) | 40분 |

2026-09-06 밤에 이 「전체 빌드」를 돌리다 디스크가 0 이 됐다(빌드 전 여유 21GB). 주간 소식 하나 갱신하려고
대장 전체를 다시 조립할 이유가 없다.

## 2. 원칙

1. **단위(unit) = 원천 하나.** 단위마다 자기 크롤·빌드·적재·파생이 있고, 자기 주기로 혼자 돈다.
2. **입력 지문으로 건너뛴다.** 단위는 입력 파일의 해시(또는 최신 날짜)를 장부에 적고, 지문이 같으면 아무것도 안 한다.
3. **파생은 입력을 선언한다.** 파생 배치마다 「무엇을 읽는가」를 적고, 그 입력의 버전이 마지막 실행 뒤 바뀐 것만 돈다.
4. **전체 빌드는 분기 대장 단위 하나뿐이다.** 그것도 디스크 여유를 먼저 재고(≥40GB), 필요한 마트만 펴고, 끝나면 중간 파일을 지운다.
5. 자동 스케줄러는 안 붙인다(기존 결정). 단위가 가벼워지면 손으로 돌리는 것으로 충분하다.

## 4. 버전 관리

지금 있는 것: `master.master_loads`(적재 한 번 = 한 줄 · source·rows·status) · `master.master_version`(전역 번호 하나).
없는 것: **원천의 입력 지문**과 **파생이 무엇을 읽었는가**.

### 4-1. 원천 장부 `master.source_version`

| 칸 | 뜻 |
|---|---|
| `unit` | 단위 이름(`news.notice`·`sales`·`ledger` …) |
| `cadence` | `weekly`·`monthly`·`quarterly`·`semiannual`·`yearly` |
| `input_sig` | 입력 지문 — 파일들의 (경로·크기·mtime) 해시. 증분 원천은 「가장 최신 줄의 날짜/번호」 |
| `version` | 이 단위가 몇 번째 판인지(적재 성공마다 +1) |
| `loaded_at` | 마지막 성공 |
| `rows` | 적재 줄 수 |

단위는 시작할 때 지문을 재고, 장부와 같으면 「바뀐 것 없음」으로 끝낸다.

### 4-2. 파생 장부 `master.derive_run`

| 칸 | 뜻 |
|---|---|
| `step` | 파생 이름(`build_sale_est` …) |
| `inputs` | 읽는 단위·파생 이름 목록(코드에 선언) |
| `input_versions` | 실행 당시 입력들의 version 스냅샷(jsonb) |
| `ran_at` · `status` | |

파생은 **선언한 입력 중 하나라도 version 이 스냅샷보다 크면** 돈다. 아니면 건너뛴다. 이게 지금 없어서 소식 하나 갱신에도
임대추정 33분이 따라 돌았다.

### 4-3. 선언 자리 — `pipeline/units.py` 한 파일

```python
UNITS = {
  "news.notice": dict(cadence="weekly",
      crawl=["scripts/urban/fetch_notices.py", "--pages", "3"],
      load=["scripts/load_urban_notice.py"],
      inputs=["data/raw/_urban_notice/notices.jsonl"]),
  "sales": dict(cadence="monthly",
      crawl=[...RTMS...], build=["data/tools/build_sales.py"],
      load=["pipeline/loader.py", "--source", "sales_history", "--csv", ...],
      inputs=["data/raw/rtms/*.csv"]),
  ...
}
DERIVES = [
  dict(step="build_area_event", reads=["news.notice","news.press","news.g2b","news.facility","news.permit","news.zones"],
       run=["scripts/build_area_event.py"], then=["scripts/load_urban_notice.py"]),
  dict(step="build_sale_est", reads=["sales","land_adjust","build_income_cap","build_bldg","gongsi"], run=[...]),
  ...
]
```

`run_pipeline.sh --unit news.press` 는 그 단위만, `--cadence weekly` 는 그 주기의 단위 전부와 뒤따르는 파생만 돈다.
`STEP=build` 전체 실행은 `--unit ledger` 로만 남긴다.

## 5. 디스크

- 전체 빌드 전 `df` 로 여유를 재고 **40GB 미만이면 시작하지 않는다.**
- `hub_csv` 가 마트를 통째로 펴는데(11GB) 단계마다 필요한 마트만 펴고 끝나면 지운다.
- 중간 jsonl(`data/tools/_*.jsonl`)·SQLite·`data/exports/_load` 는 적재 성공 뒤 지운다(재생성 가능).
- 작업 디렉터리를 외장 볼륨으로 돌릴 수 있게 `BT_WORK_DIR` 하나로 모은다.
- Docker VM 디스크(65GB)는 따로 본다 — 옛 세대 표(`_v5`)와 로그.

- **지문에 mtime 을 쓰면 안 된다.** `fetch_notices.py` 는 새 글이 0건이어도 jsonl 을 통째로 다시 쓴다.

## 9. 첫 실주행에서 드러난 것 (2026-09-06 밤)

`--cadence weekly` 를 끝까지 돌리자 **두 해 묵은 침묵이 같이 나왔다.** 단위 실행기가 없어서 아무도 안 부르던 배치들이다.

### 적정가 배치가 죽어 있었다
매력도를 빼면서 `report_calc.appraise()` 의 첫 인자(점수)를 없앴는데 **부르는 쪽 셋을 안 고쳤다** —
`build_sale_est.py:161` · `measure_radius_effect.py:104` · `report_calc.py` 자체검사.
보고서 화면(`generate_report.py:511`)은 이미 4인자라 멀쩡했고 **배치만 TypeError** 였다.
`verification-gap-db-to-screen` 의 반대 방향이다: 화면이 도는 것은 배치가 도는 증거가 아니다.

### 필지 원장의 용도지역·법정 건폐·용적이 통째로 비어 있었다
`master.parcels` 898,367줄 중 `use_zone`·`legal_bcr`·`legal_far` 가 **0건**.
따라서 `master.building_legal` 이 **0줄**이었고 검색의 법정 필터·여유 칸이 전부 비었다.
`scripts/load_parcel_luris.py`(`data/exports/luris/parcel_luris.csv.gz`, 7.7MB) 를 실으니
용도지역 896,164 · 규제 896,965 · `building_legal` 562,886줄(용적 커버리지 94.7%).

**이 되붙임은 필지를 다시 적재할 때마다 같이 돌아야 한다.** `parcels.csv` 에 없는 값이라서다.
대장 단위의 적재 줄에 `load_parcel_luris` · `load_road_width` · `load_floor_outline` · `fill_building_parcels` 를 넣었다.

### 건물↔필지 구멍
`fill_building_parcels.py` 실행: **57,228 → 9,253**. 남은 것은 필지 원장에 지번 자체가 없는 건물이다.
그 덕에 `building_legal` 커버리지가 올랐고 `build_building_legal` 의 자체 대조(건물 상세 산식과 1,000동 비교)는 어긋남 0.

### 검증
`qa/run.sh data screen ui` — 통과 3 · 실패 0 · 화면 17 ✓.

## 10. 대장 단위 첫 실주행 (2026-09-06 밤)

`scripts/run_unit.py --unit ledger --no-crawl`. 빌드 28단계 **1,555초**에 완주, CSV 12개 생성.
중간산물 10.9GB 를 빌드 직후 스스로 치워 디스크는 43 → 23GB 로 안전하게 끝났다. 배선 둘이 의도대로 작동했다:
압축본 펴기(`archive_seoul.py --restore`)와 자동 청소(`clean_after_build`).

**적재는 세 번째에서 막혔다.** 원인 셋을 고쳤다.

### ① 행수 문턱을 살아 있는 표와 견주면 안 된다
`building_parcels` 새 판 682,492줄 vs 살아 있는 표 730,467줄 = 0.934 < 0.95 → 스왑 거부.
빌드가 잘못한 게 아니다. **적재 뒤에 덧대는 `fill_building_parcels.py` 47,975줄**이 살아 있는 표를 불린 것이다.
→ 로더가 `master.master_loads` 의 **지난 적재분(`rows_out`)** 과 견준다. 줄이 진짜 줄어드는 사고는
   그대로 잡히도록 **살아 있는 표와 지난 적재분 중 작은 쪽**을 기준으로 쓴다.

### ② 실패한 단위가 파생을 끌고 돌았다
실패 경로에서도 `bump()` 가 판을 올려, 그 단위를 읽는 파생 여덟이 「낡음」이 되어
**반쯤 적재된 표 위에서** 임대추정·적정가·점수를 다시 계산했다.
→ 실패는 `status='failed'` 만 적고 **판을 올리지 않는다**.

### ③ 디스크 문지기가 복구를 막았다
`--phase load` 로 적재만 다시 하려는데 40GB 문지기에 걸렸다. 적재는 압축본을 펴지도 중간산물을 쓰지도 않는다.
→ 문지기는 **빌드가 실제로 도는 실행에서만** 잰다. `--phase crawl|build|load` 를 붙였다.

### 함께 드러난 것
- `export A=... B="$A"` 는 **zsh 에서 B 가 빈다**(같은 문장 안의 옛 값을 본다). 적재 열 개가 전부
  `database "iseung-ug" does not exist` 로 죽었다. 로더는 `DATABASE_URL` 하나만 본다.
- **필지를 새로 적재하면 LURIS 되붙임이 날아간다.** `parcels_v8` 에 용도지역·법정 건폐·용적이 다시 0 이 됐고
  `building_legal` 이 0줄이 됐다. 대장 단위 적재 줄에 `load_parcel_luris` 가 있지만 ①에서 멈춰 도달하지 못했다.

## 14. 단위 분리 · 검증 분리 (2026-09-07 밤)

대표 지시: 「크롤부터 적재 후 최종검증까지를 각 데이터의 주기에 맞게 분리하자. 빌드만 나누는 게 아니라.」
「오늘은 공시지가 하는 날」이면 공시지가만 받고 싣고 검증한다. 공시지가 하나를 본보기로 끝내고 그 틀을 나머지에 폈다.

### 마디가 넷이 됐다
`① 크롤 → ② 빌드 → ③ 적재 → ④ 검증`. 넷째가 없었다.

| 자리 | 무엇을 재나 | 깨지면 |
|---|---|---|
| 받은 것 확인(`verify_files`) | 파일 개수·크기 하한·첫 4KB 의 머리글 | **적재로 안 넘어간다** |
| 단위 검증(`verify`) | 자기 표의 불변식 | 판을 안 올린다 → 뒤따르는 파생도 안 돈다 |
| 파생 검증(`DERIVE_VERIFY`) | 자기가 낸 결과 | 판을 안 올린다 |

검사 하나 = `(이름, SQL)`. SQL 은 **두 칸**을 낸다 — 참/거짓과 사람이 읽을 값.
받은 것 확인은 `(이름, glob, 최소바이트, 머리글, 최소 파일 수)`.

지금 **단위 34개 · 파생 15개 · 받은 것 11개**. `qa/data/qa_data.py` 에 뭉쳐 있던 검사를 주인에게 옮긴 것이다.

### 공시지가를 뗐다 — 본보기
연 1회(5월 말) 갱신인데 `build_land_master.py` 안의 한 함수라, 공시지가만 갱신하려 해도 대장 28단계를 다 돌았다.
시계열은 공간 조인이 필요 없다(D150 dbf 의 PNU·금액 두 칸이면 된다) — `scripts/build_gongsi_series.py` 로 뗐다.

    scripts/run_unit.py --unit gongsi

검증 다섯: 연도 구간 1990~2026 · **빠진 연도 없음** · 2,800만 줄 · 올해 값 88만 필지 · 필지 원장에 98.7% 결합.
둘째가 2026-08-31 사고(26년치→11년치)를 다시 못 나게 막는다.

### 필지는 아직 못 뗀다
`export_parcels.py` 가 넷을 읽는다: `_land_master.jsonl` · `_spatial_ALL.json`(공간 조인) ·

교통도 마찬가지로 남았다 — 자기 표가 없고 `buildings` 의 칸이다(승강기와 같은 처지).

## 16. 되풀이되는 모양 — 「원천은 뗐는데 값이 화면까지 안 온다」

승강기·공시지가에서 **똑같은 모양**이 나왔다. 별도 원천인데 **값이 대장 빌드 안에 구워져 있어서**,
원천만 갈면 시계열·원장은 새것인데 화면이 읽는 칸은 옛것으로 남는다.

| 값 | 화면·파생이 읽는 자리 | 굽는 곳 | 어떻게 풀었나 |
|---|---|---|---|
| 승강기공단 | `buildings.elevator_ext` | `build_integrated`→`build_sqlite`→`export_seoul` | `load_elevator_ext.py` 로 적재 뒤 되붙임 |
| 공시지가 | `buildings.gongsi_latest` | `export_seoul`(SQLite prices) | `fill_gongsi_latest.py` 로 적재 뒤 되붙임 |
| 용도지역·규제 | `parcels.use_zone`·`legal_bcr` | (대장 CSV 에 없음) | `load_parcel_luris.py` — 전부터 이 방식이었다 |
| 도로폭 | `building_road` | `build_road_width` | `load_road_width.py` — 같은 방식 |
| 교통 | `buildings.station_dist`·`subway_json` | `build_transit`→`integrated` | **아직 안 뗐다** |

**되붙임은 두 곳에 걸어야 한다.** 자기 단위의 적재 줄에 하나(원천이 갈릴 때),
대장 단위의 적재 줄에 하나(대장이 새 세대를 실어 그 칸을 다시 구울 때). 한쪽만 걸면 반드시 어긋난다.

### 실측 (2026-09-07)
`gongsi_series` 를 3,456만 행으로 새로 실은 뒤 `buildings.gongsi_latest` 와 대조하니
**4,892동이 어긋나 있었다.** 적정가·층별임대·건물임대·가격지수 넷이 그 칸을 읽으므로
그대로 두면 옛 지가로 계산한다. 파생 넷의 `reads` 에 `gongsi` 를 넣었다 —
5월에 공시지가가 갱신되면 그 넷이 자동으로 따라 돈다.

### 이걸 잡는 검증
    ("건물의 gongsi_latest 가 시계열과 같을 것",
     "... where b.gongsi_latest is distinct from l.price")
