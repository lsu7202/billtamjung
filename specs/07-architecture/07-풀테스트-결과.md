# 파이프라인 풀테스트 결과 (2026-08-02)

> **from-scratch 실행**: raw 백업 → 삭제 → 전체 재크롤 → activate → build_all → loader → test DB → baseline 대조.
> 목적: 크롤부터 DB까지 엔드투엔드가 데이터를 정확히 재생산하는지 실증.

## 절차(실제 실행)
1. **백업**: 전체 raw(32GB)를 zstd 압축 → `data/_raw_backup_20260802.tar.zst`(3.66GB, 6.1x·445항목 검증). 빌탐정.db → `.bak`.
   - 디스크 23GB<raw 32GB라 통짜 복사 불가 → dbf/txt 고압축성 활용해 압축 백업.
2. **삭제**: `data/raw` 전삭제(→50GB 확보).
3. **재크롤**: `crawl_all.py --group all` → 스테이징. **전 소스 성공** — 실거래 42CSV·HUB djy4+kcy_01·승강기·임대·LSMD 9종·C_UQ161·토지특성 25구·공시지가·교통·지가변동률.
4. **activate**: 스테이징 → 정규 raw(HUB→extract_seoul, LSMD→dir, NA→토지특성/·D150, 승강기 zip→CSV). raw 재구성 확인(35GB).
5. **역사 공시지가 복원**: 재크롤 불가분(공시지가 2016~2025 dir 11개 + 1990~2015 백필 CSV 26개)을 아카이브에서 선택 복원.
6. **build_all**(15단계, 19분) → export → **loader 5소스** 원자스왑 → test DB(billtamjung_test).

## 발견·수정한 버그
1. **build_all 구별인자 누락**: `spatial_join`·`legal`·`regulations`·`annex`·`transit`가 시군구 인자 스크립트(기본=단일 구!) → build_all이 `ALL`/`11` 전달하도록 수정. (없었으면 1개 구만 처리)
2. **stale 의존 `_sales_area.json`**: `build_sales`가 동시세(dong_sales) 폐기했는데 `build_sqlite`가 계속 읽어 크래시 → 파일 있을때만 적재하도록 수정.
3. **승강기 포맷 변경**: data.go.kr 승강기가 CSV 2개→**zip**으로 바뀜 → `activate.py`에 승강기 zip 내부 CSV 추출 분기 추가.
(운영: 강제종료된 loader의 좀비 advisory lock → `pg_terminate_backend`로 해소.)

## 결론
- **from-scratch 엔드투엔드 완전 검증**: 빈 raw → crawl → activate → build_all(15단계) → export → loader(원자스왑) → Postgres. 데이터 월간 갱신 오차 내 정확 재현.
- 자동로그인·월경로 해소·C_UQ161·지가변동률·승강기zip 전부 실동작.
- **상태**: raw=재크롤 최신본(35GB) · 빌탐정.db=재빌드(2.39GB, `.bak`=이전본) · 아카이브 백업(`_raw_backup_20260802.tar.zst`) 보존 · **프로덕션 Postgres master 미변경**(test DB로만 검증).
