> 2026-09-26 확정분. 구현은 파이프라인 작업이라 같이 한다. 「확인 대기」 표시는 아직 정하지 않은 것.

## 1. 원천마다 맡는 일

| 화면 | 원천 | 말하는 것 |
|---|---|---|
| 층별 임대정보 | **카카오·네이버 화면 크롤링** + 팀 입력 | 지금 몇 층에 누가 있다 |
| 입주 이력 | 로컬데이터(인허가) + 상가정보 | 언제 누가 들어왔다 나갔다 |

- 인허가 「영업」은 폐업 신고를 안 하면 남는다(직권말소·취소로 뒤늦게 지운 것 16.7만 건). **지금 있는지는 말하지 못한다.**
- 상가정보는 인허가와 대조할 수 있는 업체 중 9%가 이미 폐업했고, 폐업 뒤 중위 3년 남아 있다.
- 지금 있는지는 크롤링이 본다. API 가 아니라 **카카오맵 화면이 부르는 데이터 주소를 직접** 부른다.
- **네이버는 버렸다**(2026-09-26 대표). 검색 주소는 캡차가 걸리고, 주소 정보 주소는 초당 10번에서 200개쯤 뒤,
  초당 4번에서도 HTTP 400 으로 연속해서 막았다. 한 주소에 20곳까지만 주기도 한다(시험 200주소 중 41개가 잘림).
  캡차를 풀거나 IP 를 돌려 막힘을 피하는 방법은 쓰지 않는다.

**0단계 결과(2026-09-26)**

| | 카카오 (`map.kakao.com/api/v1/mapsearch/map?q=도로명`) |
|---|---|
| 속도 | 한 번 0.27초. 초당 10번 · 8줄로 실패 0 |
| 한 번에 | 15곳, 쪽을 넘겨 전부(가산동 327-30 = 85곳) |
| 층 | **장소의 54%에 층·호가 주소 끝에 붙어 온다**(「3층 301호」 · `new_address_disp` 마지막 토막) |
| 업종 | 전체 경로(`cate_name_depth1~5`: 의료,건강 > 병원 > 한의원) |
| 거르기 | 그 주소에 가게가 없으면 카카오가 낱말로 근처 가게를 채워 준다(「가로수길 13」 → 논현로163길 「패션랩13」). **도로명이 같은 장소만** 남기고, 섞이기 시작하면 쪽 넘기기를 멈춘다 |
| 도로명 | 대장에 도로 이름이 빠진 도로명 43개(「서울특별시 강남구 24」)는 건너뛴다 |
| 쓰지 않는 것 | 브라우저의 로그인 쿠키 · `x-kmap-captcha-token` |

## 2. 0단계 — 표본 조사 (코드보다 먼저)

30동 표본으로 잰다. 이 숫자로 수집 방법을 확정한다.

| 잴 것 | 왜 |
|---|---|
| 곳마다 업체 수(카카오·네이버·지금 카카오 API) | 크롤링이 API 보다 얼마나 더 찾나 |
| **층이 나오는 비율**(장소 상세의 주소·상세주소) | 안 나오면 층별이 전부 층 미상 |
| 카카오 업종이 **전체 경로**로 나오나, 네이버는 무엇을 주나 | 업종 나무(§6)의 재료 |
| 두 곳 겹치는 비율 · 이름이 다른 유형 | 업체 묶기(§5) 규칙의 재료 |
| 페이지가 값을 무엇으로 받아 오나 | 화면을 그릴지, 페이지가 부르는 데이터를 읽을지 |
| 막히는지(속도 제한·차단) | 수집 속도 |

## 3. 수집 대상 · 주기 · 차례

**대상 = 우리 도로명 주소 전체 492,960개**(2026-09-26 대표). 같은 도로명을 쓰는 건물(아파트 단지 등)은 한 번만 묻는다.
**목표: 한 바퀴를 하루 안에.** 초당 10번 · 8줄이면 계산상 약 15시간.

| 무엇 | 주기 |
|---|---|
| 전체 | **분기 1회** — 상가정보와 같은 주기 |
| 팀 매물 건물 | **월 1회** — 중개인이 지금 상태를 자주 본다 |

**첫 수집 차례**(한 바퀴에 석 달이 걸리므로 무엇부터 채우느냐)

```
① 팀 매물 건물  →  ② 사용자가 열어 본 건물  →  ③ 나머지 대상
```

## 4. 수집 규칙

| 항목 | 규칙 |
|---|---|
| 묻는 주소 | **도로명**. 대장 지번은 대표지번 하나뿐이라 부속지번으로 등록된 가게가 빠진다(연지동 275-1 로 3곳 · 275-2 로 경희한의원·노래카페 · **도로명으로 전부**). 지번 질의는 도로명이 없는 건물에만(다음 판) |
| 건물에 붙이기 | 장소의 지번이 건물 필지 중 하나이거나 도로명이 같을 때만 |
| 층 | 페이지의 층 원문 → `core/floor_label` 로 정규화. 없으면 로컬(폐업 포함)·상가정보에서 이름으로 빌린다(`tenants.past_floors`) |
| 확인한 날 | 이번 수집에 보이면 `last_seen` = 수집일 |
| **없어짐** | **다음 수집 때 안 보이면 없어진 것**(`gone_on` = 그 수집일). 단 **그 건물 수집이 실패했으면**(오류·차단·0건 응답) 없어짐으로 치지 않는다 |
| 속도 | 요청 사이 간격 · 동시 1~2개. 바뀐 곳만 다시 |

**크롤링 업체도 입주 이력에 들어간다**(2026-09-26 대표). 입주 이력은 지금 있는 업체와 지나간 업체를 다 담는다.
층별 임대정보에 있는 업체가 입주 이력에서 빠지는 게 아니라, 입주 이력에 **끝난 날이 생기는** 것이다.
인허가·상가정보에 없는 업체(사무실 등)도 크롤링으로 들어온다.

| | 규칙 |
|---|---|
| 시작 | 인허가·상가정보 개업일이 있으면 그것. 없으면 **첫 수집 때 이미 있던 업체는 모름**, 뒤 수집에서 새로 보인 업체는 처음 본 수집일(`first_seen`) |
| 끝 | 크롤링에서 없어지면 그 수집일(`gone_on`). 뒤에 **로컬데이터·상가정보에 폐업일이 생기면 그 날로 덮는다** |
| 지금 있음 | 크롤링에 보이는 동안 |

인허가·상가정보 폐업일이 크롤링 `gone_on` 보다 늦어도 **폐업일로 덮는다**(2026-09-26 대표 · 기준을 하나로 통일).

## 5. 업체 묶기 — 카카오 ↔ 네이버, 같은 건물 안에서만 (네이버를 버려 지금은 안 쓴다)

1. 전화번호가 같으면 같은 업체
2. 이름을 접어서 같거나 앞머리(3자 이상)가 겹치면 같은 업체.
   접기 = 괄호·(주)·띄어쓰기 제거 · **건물이 있는 동 이름 제거**(미스터연지동순두부 → 미스터순두부) · 끝의 「○○점」 제거
3. 둘 다 아니면 다른 업체

LLM 은 쓰지 않는다. 틀린 짝이 나오면 **이름 짝 회귀 코퍼스**에 넣어 규칙을 늘린다(파서 코퍼스와 같은 방식).

## 6. 업종 나무

「병원」으로 찾아도, 「피부과」로 찾아도 피부과가 걸려야 한다. 지금 카카오 키워드 검색이 그렇다.
크롤링 페이지가 「피부과」 하나만 줄 수 있어 **우리 쪽에 나무가 있어야** 한다.

- **카카오 나무가 기준이다.** 카카오 페이지의 전체 경로(「의료,건강 > 병원 > 피부과」)로 부모-자식을 채운다.
- **네이버는 카카오 나무에 맞춘다.** 네이버 이름을 카카오 마디에 잇는 `alias` 를 둔다.
- 어디에도 없는 이름은 그 이름 하나로 저장하고 **「사전에 없는 업종」** 목록에 모아 나무에 붙인다.
- 업체엔 **조상까지 펼쳐** 저장한다(`cat_nodes` = {의료·건강, 병원, 피부과}). 검색은 `낱말 = ANY(cat_nodes)` 하나다.
  나무에 부모가 새로 붙으면 `cat_nodes` 를 다시 펼친다.

기존 `ref.biz_category`(75줄)는 상권 7갈래로 가르는 평평한 표라 이 용도가 아니다. 그대로 둔다.

## 7. 스키마

```
master.place                -- 한 출처의 한 장소 (카카오 1곳 = 1줄, 네이버 1곳 = 1줄)
  id           bigserial
  source       text        -- kakao | naver
  source_id    text        -- 그쪽 장소 번호. (source, source_id) 유일. 다음 수집 때 같은 장소를 알아보는 열쇠
  name         text
  cat_path     text        -- 페이지의 업종 원문
  cat_tokens   text[]      -- 원문을 낱말로 쪼갠 것
  phone        text
  road_addr    text
  jibun_addr   text
  floor_raw    text        -- 페이지의 층 원문. 없으면 null
  building_pk  text        -- 주소로 붙인 우리 건물. 못 붙으면 null
  biz_id       bigint
  first_seen · last_seen · gone_on   date

master.biz                  -- 우리 쪽 「업체 하나」. 카카오·네이버 기록을 묶는다
  id           bigserial
  building_pk  text
  name         text        -- 대표 이름
  name_norm    text        -- 접은 이름(§5)
  phone        text
  floor        text        -- 정규화한 층. 크롤링 → 없으면 로컬·상가정보에서 빌림
  floor_from   text        -- crawl | localdata | sbiz (내부 검증용 · 화면엔 안 쓴다)
  cat_nodes    text[]      -- 조상까지 펼친 업종(§6)
  first_seen · last_seen · gone_on   date

master.place_crawl_log      -- 수집 한 번
  building_pk · source · 질의어 · 받은 수 · 시각 · 오류

ref.biz_cat                 -- 업종 나무 (카카오 기준)
  name · parent

ref.biz_cat_alias           -- 네이버 이름 → 카카오 마디
  source · label · name

색인  biz.name_norm (부분일치) · biz.cat_nodes (GIN) · place(source, source_id) 유일
```

링크(URL)는 저장하지 않는다. 화면에서 카카오·네이버로 가는 링크를 쓰지 않는다(§9).

## 8. 카카오 API 대체

지금 카카오 로컬 API 를 쓰는 곳은 둘이다. 카카오 로그인(`social.py`)은 로컬 API 와 무관하게 그대로 둔다.

### 8-1. 장소 목록 → `tenants.biz_for(building_pk)`

| | 지금 (`places.places_for`) | 바꾼 뒤 |
|---|---|---|
| 원천 | 화면 열 때마다 카카오에 묻는다 | `master.biz` 중 `gone_on IS NULL` |
| 돌려주는 것 | 이름 · 업종 · 전화 · 링크 | 이름 · 층 · 전화 · **확인한 날** |
| 쓰는 곳 | 층별 임대정보(`floors.py`) · 입주 이력 「지금 있음」(`tenants.py`) | 같은 두 곳 |

층별 API(`GET /buildings/{pk}/floors`)는 모양을 그대로 두고 `checked_on`(그 건물 `last_seen` 중 가장 최근) 하나를 더한다.

### 8-2. 「입주 업종」 검색 → 검색 SQL 안의 한 줄

| | 지금 (`core/kakao.keyword_search` · `search.resolve_biz`) | 바꾼 뒤 |
|---|---|---|
| 범위 | 카카오가 전국을 뒤지니 지역·영역을 사각형으로 넘기고 45건이 넘으면 넷으로 쪼개 다시 부른다 | 업체가 이미 건물번호를 달고 있다. **검색이 원래 거는 지역·영역(폴리곤) 조건이 그대로 범위** |
| 건물 찾기 | 카카오 주소 → 필지번호 → 건물 | 필요 없다. 수집할 때 붙였다 |
| 흐름 | 검색 전에 낱말마다 카카오를 부르고 건물번호 집합을 만든다 | `EXISTS (… master.biz WHERE building_pk = … AND gone_on IS NULL AND (name_norm 에 낱말 OR 낱말 = ANY(cat_nodes)))` |
| 「3곳 이상」·줄의 개수·상호명 | 카카오 결과를 센다 | 같은 SQL 에서 센다 |
| 사라지는 것 | `_area_rect` · 타일 쪼개기 · 45건 상한 · 「잘렸다」 경고 · 「주소 못 읽음」 · `resolve_biz` 전 단계 | |

화면 「입주 업종」 필터와 모델 「입주업체」 조건은 이름과 모양을 그대로 둔다. 모델 설명의 「카카오맵 검색창에 치듯」만 「업체 이름이나 업종 낱말」로 바꾼다.

## 10. 전환 순서

| | 전환 | 그 전까지 |
|---|---|---|
| 층별 임대정보 · 입주 이력 | 건물마다 수집되는 대로 | **수집 안 된 건물은 지금 방식 그대로**(원장 + 카카오 API) |
| 검색 「입주 업종」 | **서울 대상 전체 1회 수집이 끝난 뒤 한 번에** | 지금처럼 카카오 키워드 검색 |
| 카카오 로컬 코드 삭제(`places.py` · `core/kakao.py`) | 둘 다 전환된 뒤 | 둔다 |

검색을 먼저 바꾸면 수집 안 된 동네에서 「피부과 0곳」이 나와 틀린 답이 된다.

**검색 전환 기준** — 같은 낱말(피부과·병원·카페·스타벅스·학원)을 세 동네에서 카카오 API 와 우리 DB 로 나란히 뽑아,
카카오가 찾은 것의 몇 %를 우리가 잡는지 잰다. **기준 95%**(2026-09-26 대표) — 밑이면 전환하지 않는다.
이 비율은 100%가 끝이다. 네이버에서만 찾은 업체는 따로 센다(「카카오엔 없고 우리만 찾은 것」).
크롤링이 제대로 되면 이쪽 숫자가 더해져 카카오 API 보다 많이 찾는다.

## 11. 파이프라인 단위 · 차례

`pipeline/units.py` 에 `places.crawl` 단위(수집 → 붙이기 → 적재 → 검증).

```
0 표본 조사 → 1 스키마 → 2 수집기 → 3 업체 묶기 + 코퍼스 → 4 업종 나무 → 5 층 채우기
  → 6 층별·입주 이력 전환 → 7 검색 전환 → 8 카카오 로컬 코드 삭제
```

검증(QA): 화면이 DB 를 맞게 읽나(`qa/run.sh screen`) · 업체 묶기 코퍼스 · 검색 전환 대조(§10).
