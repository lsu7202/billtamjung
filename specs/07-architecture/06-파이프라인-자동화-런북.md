# 데이터 파이프라인 자동화 · 런북

> **평소 갱신은 `scripts/run_unit.py` 로 한다**(2026-09-07~). 아래 `run_pipeline.sh` 는
> **첫 구축·프로덕션 초기 적재용**으로 남긴다 — 어느 원천이 바뀌었든 대장 전체 빌드가 따라 돈다.
> 크레덴셜=`scripts/.env.pipeline`(gitignore) + `backend/.env`.

## 평소 갱신 — 원천 단위 (정본: [07-원천별-증분-파이프라인.md](07-원천별-증분-파이프라인.md))

```
scripts/run_unit.py --list                 # 단위·주기·판·마디 한눈에
scripts/run_unit.py --unit gongsi          # 「오늘은 공시지가 하는 날」
scripts/run_unit.py --unit news.press      # 「오늘은 보도자료 하는 날」
scripts/run_unit.py --cadence weekly       # 그 주기 것 전부 + 뒤따르는 파생
qa/run.sh units                            # 검증 67가지 전부 훑기
```

한 단위는 **① 크롤 → ② 빌드 → ③ 적재 → ④ 검증** 네 마디다.
**검증이 깨지면 판을 안 올리고, 판이 안 오르면 그 단위를 읽는 파생도 안 돈다.**

| 주기 | 단위 | 대략 걸리는 시간 |
|---|---|---|
| 주 | `news.notice` · `news.press` · `news.g2b` | 각 1분 + 소식 합침 1분 |
| 월 | `news.facility` · `stores.localdata` · `sales` · `land_adjust` | 5~20분 |
| 분기 | `news.permit` · `stores.sbiz` · `elevator` · `rent_index` · **`ledger`** | 승강기 1.5분 / 대장 84분 |
| 반기 | `news.zones` | 5분 |
| 연(5월 말) | `gongsi` | 6분 + 파생 30분 |

**대장(`ledger`)만 전체 빌드다.** 디스크 여유 **45GB** 를 먼저 재고 시작한다 —
0 이 되면 Postgres 가 죽고 도커도 안 켜진다(2026-09-06·07 에 두 번 겪었다).

**되붙임은 두 곳에 걸려 있다.** 자기 단위의 적재 줄과 대장 단위의 적재 줄이다
(`load_parcel_luris` · `load_road_width` · `load_floor_outline` · `fill_building_parcels` ·
`load_elevator_ext` · `fill_gongsi_latest`). 한쪽만 걸면 대장을 다시 실을 때 값이 어긋난다.

```
scripts/crawl_all.py      크롤(실거래·HUB·교통·임대·승강기·V-World[자동로그인])  → data/raw/_dl (스테이징)
```

## 적재 뒤에 오는 것 — **여기가 오래 비어 있었다**(2026-08-30 배선)

빌드 16단계 중 export 로 나가는 것은 5개뿐이고, loader 가 아는 원천도 그 5개다.
나머지는 **파이프라인 밖에서 손으로** 돌고 있었다. 그래서 이런 일이 났다:

- `master_loads` 에 기록된 적재가 5건·2026-07-21 뿐이었다 — 「언제 덮였나」에 답할 수 없었다
- `building_score` 0행 · `building_redevel` 0행 — 스크립트는 멀쩡한데 **한 번도 안 돌린 것**
- `floor_outline` 은 **적재 코드 자체가 없었다** — 손으로 넣다가 8/02 판 옛 CSV 로 덮여
  층 표기 정규화가 되돌아갔고 지하 21만 층이 두 달간 지상 요율로 계산됐다
- `parcels` 세대 스왑이 용도지역·규제 네 칸을 **지우고 갔다**(원장에서 따로 오는 값이라 CSV 에 없다)

이제 적재 뒤에 **순서대로** 붙는다. 순서가 곧 의존이다:

```
4) 되붙이기   parcel_luris(용도지역·법정건폐/용적·규제) · road_width · floor_outline
5) 파생 배치  ① 참조표   sanggwon · trade_area · subway_stations · building_redevel
                        land_adjust · sanggwon_rent_series · sale_price_index
              ② 계산값   building_calc                         (대장이 비운 용적률·건폐율 — 검색·분석 전용)
              ③ 임대     floor_rent_est → building_rent_est    (층이 먼저, 건물은 그 합)
                        → income_cap                           (임대추정 ÷ 실거래라 임대 뒤여야 한다)
              ④ 적정가   building_sale_est                     (임대·cap·참조표를 읽는다)
              ⑤ 점수     building_score                        (계산 용적률·정비구역·공시추세를 읽는다)
6) 검증       qa/data/qa_data.py — 층 표기·면적·임대 눈금·지하 깊이·파생 배치·규제 커버리지
              **실패하면 여기서 멈춘다**(2026-08-30). 예전엔 경고만 냈다.
```
- 파생 배치는 하나가 실패해도 **멈추지 않고** 다음으로 간다(옛 값이 남는다는 경고만 낸다).
  다만 마지막 `qa_data` 는 **실패하면 파이프라인을 멈춘다** — 틀린 값이 화면·보고서·계약서로
  그대로 나가기 때문이다. 산식만 고쳤으면 `STEP=derive scripts/run_pipeline.sh` 로 파생부터 다시 돈다.
  대신 `master.master_loads` 에 성공·실패를 남기고, 마지막 `qa_data` 가 빈 표를 잡는다.
- **인터프리터가 둘이다.** SHP 을 읽는 셋(sanggwon·trade_area·building_redevel)은 `data/.venv`,
  DB 만 만지는 나머지는 `backend/.venv`. `derive ... gis` 로 가른다. 섞으면
  `ModuleNotFoundError` 로 조용히 건너뛴다.

## 검증 테스트 (2 tier)

### Tier 1 — 안전(비파괴): 현재 raw/DB로 재현성 확인
프로덕션 뷰를 건드리지 않고 **별도 테스트 DB**에 재적재해 baseline과 대조.
```bash
# 1) 테스트 DB 생성 + 스키마
createdb -h localhost -p 55432 -U postgres billtamjung_test
DATABASE_URL=postgresql://postgres:PW@localhost:55432/billtamjung_test ./db/apply.sh
# 2) 현재 빌탐정.db → export → 테스트DB 적재
STEP=build EXPORT_DIR=/tmp/exp \
  DATABASE_URL=postgresql://postgres:PW@localhost:55432/billtamjung_test \
  scripts/run_pipeline.sh
# 3) 카운트 대조: billtamjung_test.master.* == baseline(±허용오차)
```
- **build 재빌드도 검증하려면**: raw는 현행 유지, `빌탐정.db`만 백업 후 `build_all.py`로 재생성 → 두 db 카운트/샘플 diff.

### Tier 2 — 풀 from-scratch(파괴적, 사용자 입회 권장)
raw·빌탐정.db·Postgres 전부 비운 뒤 크롤부터 재현. **32GB 재크롤 + 수시간 빌드** → 무인 실행 비권장.
```bash
# 백업
pg_dump "$BT_DATABASE_URL" > /backup/pg_$(date +%F).sql
tar czf /backup/raw_$(date +%F).tgz data/raw          # (32GB, 시간·디스크 주의)
cp data/빌탐정.db /backup/
# 4건 보존물 별도 대피(위 목록) → raw 초기화 → run_pipeline.sh 전체 → baseline 대조
```

## 검증이 잡는 것 — 임대 산식이 조용히 밀리는 모양  *(2026-08-30)*

v4(공시지가 주축)를 넣고 나서 **적재된 값을 손으로 층별 검산하다가** 버그를 찾았다.
그때는 이 검사가 없었다. 지금은 `qa_data` 가 셋을 본다.

| 검사 | 기준 | 무엇을 잡나 |
|---|---|---|
| 층 서열 | 지하1 < 1층 · 2층 < 1층 | 층 판정이 뒤집힘 |
| **지하 깊이** | 같은 건물 안 지하3 ÷ 지하1 ≤ 1.0 | 층대를 뭉쳐 깊이를 못 봄 |
| **임대 눈금** | 호가 대비 0.70~1.00 | 산식이 통째로 밀림 |

지하 깊이는 **같은 건물 안에서** 재야 한다. 건물을 섞어 중앙값을 비교하면 깊은 지하가 더
비싸게 나오는데, 그건 산식이 아니라 깊은 지하가 큰 건물·비싼 땅에만 있기 때문이다.
처음에 그렇게 짰다가 멀쩡한 데이터를 실패로 잡았다.

임대 눈금이 1.0 이 아닌 이유: 우리는 실계약(부동산원) 기준이고 잣대는 호가다.

## 적재 목록 = 빌드 목록  *(2026-08-09 추가 · 사고 기록)*

`build_all.py`가 만드는 산출물과 `run_pipeline.sh`가 **싣는** 목록이 서로 달라서
프로덕션에 `road_segment`가 비어 있었다. 만들기는 하는데 안 싣고 있었다.

빌드 단계를 추가하면 **적재 단계도 같이 추가한다.** 둘은 한 쌍이다.

| 산출물 | 빌드 | 적재 |
|---|---|---|
| buildings·parcels·building_parcels·gongsi_series·sales_history | `build_all.py` | `loader.py --source` |
| **road_segment · building_road** | `build_all.py`(road_width) | **`scripts/load_road_width.py`** ← 빠져 있었음 |
| **building_score**(매력도·활용유형·매도가능성) | — (원천 적재 후 계산) | **`scripts/build_building_score.py`** |

`building_score`는 빌드 산출물이 아니라 **적재된 원천 위에서 도는 파생 배치**다.
그래서 적재 목록 뒤(5단계)에 붙였다. 원천이 바뀌면 점수도 같이 다시 돌아야 한다 —
따로 돌리게 두면 프로덕션에서만 옛날 점수가 남는다(위 road_width와 같은 사고).

`loader.py`의 세대 스왑(v1→v2)은 검색이 붙는 대형 테이블용이다. 도로폭은 파생 계산의
입력이라 TRUNCATE+INSERT 전용 스크립트를 쓰되, **파이프라인 안에서** 돌게 한다.

### 컬럼을 추가하는 마이그레이션은 값 백필까지 생각한다

`0034_building_height.sql`이 `height` 컬럼만 추가했다. 값은 buildings CSV에 실려
loader가 **재적재**할 때 들어오는데, 프로덕션 buildings는 그 이전 세대라 전부 NULL이 됐다.

정기 적재 전까지 값이 필요하면 백필 스크립트를 같이 낸다 — `scripts/backfill_height.py`
(값이 있는 DB에서 `dump` → 대상 DB에 `load`. 기존 값은 안 덮는다).

뷰가 옛 목록을 들고 있었다. 정기 적재 때는 loader가 스왑 후 `CREATE OR REPLACE VIEW`로 다시
만들어 저절로 맞지만, 마이그레이션만 돌린 DB는 안 맞는다(0042가 그 다리).
