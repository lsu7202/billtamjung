> 목적: "이 값·로직은 어디에 두지?"를 판단하는 단일 기준. 새 기능/정책 변경 시 이 문서에 비춰 배치한다.

## 1. 핵심 원칙 — 3층 배치 규칙

변경 주기와 소유 주체에 따라 **세 곳 중 하나**에 둔다.

| 층 | 스키마 | 무엇을 두나 | 변경 방법 | 예 |
|---|---|---|---|---|
| **메타 레지스트리** | `ref.*` | 정책·파라미터·정의. **시간이 지나며 튜닝되는 값** | DB row(버전·active) | enum 값, 산식 가중치, 등급컷, **크레딧 비용** |
| **유저 오버레이** | `app.*` | 사용자/팀이 만든 값 | 유저 편집 | 오버레이 수정, 매물등록, 임대, 광고가, 메모 |
| **마스터** | `master.*` | 공공 원천 데이터 | loader **버전 스왑**(불변) | 건축물대장, 토지, 공시지가, 실거래 |

- **불변 식별자**(building_pk·pnu·주소·좌표·geom·sgg/bjd)는 어느 층에서도 수정 불가 — `validate_overlay` 차단(0010).
- **화면값 = master COALESCE app.overlays**(팀 스코프, `building_view`). 마스터는 절대 안 건드림.

## 2. 왜 이 구조인가 (변경 시나리오)

| 실제로 일어나는 변경 | 처리 | 재배포? |
|---|---|---|
| enum 값 추가("가격제시" 상태 등) | `ref.enums` INSERT | ❌ |
| 산식 가중치·등급컷 튜닝 | `ref.formula_params` UPDATE(+새 버전) | ❌ |
| **크레딧 비용 증감 / 새 유료기능** | `ref.credit_costs` UPDATE/INSERT | ❌ |
| 유저가 데이터 수정 | `app.overlays` upsert | ❌ |
| 공공데이터 월간 갱신 | loader 검증게이트 → 원자 뷰스왑 → version++ | ❌(무중단) |
| 마스터 새 컬럼 | 마이그레이션 + loader 컬럼목록 | ⚠️(스키마 변경) |

→ **정책·값·데이터는 전부 무재배포. 스키마 변경만 마이그레이션.** 버전(active 플래그)으로 롤백도 공짜.

## 3. 레지스트리 표준형 (formula_sets 패턴)

새 정책을 데이터화할 땐 이 형태를 복사한다:
```
ref.<policy>_sets(set_version int PK, active bool, note, created_at)
  UNIQUE(active) WHERE active            -- active는 항상 하나
ref.<policy>(set_version FK, <key>, <value>)
```
- 조회 = active 버전. 변경 = 새 버전 INSERT 후 active 이동(무중단·롤백).
- 산출물엔 **사용 시점 버전/값을 스냅샷**(예: `reports.credits_spent`, `formula_set_version`) → 과거 기록 불변.

### 3.1 크레딧 비용 (신규 적용 대상)
```
ref.cost_sets(set_version, active, note)
ref.credit_costs(set_version, action_key, cost)
  action_key: 'report_analysis'(30) · 'report_briefing'(10) · 미래 기능…
```
현재는 `config.py`(`cost_analysis/cost_briefing`) 하드코딩 → 이 테이블로 이관. `deduct_credit` 호출부가 active 버전에서 cost 조회.

## 4. 코드 seam (데이터화하지 않고 인터페이스로 유연화)

DB 레지스트리가 과한 곳은 **모듈 경계 하나**로 미래 교체를 흡수한다.

- **보고서 서술문** — `report_narrative.narrate(building, scores, comps) -> {block_key: text}`.
  렌더러는 결과를 placeholder에 바인딩만. 규칙기반(지금) ↔ AI(나중)를 **같은 시그니처 뒤에서 스왑**. 렌더러 무변경.
- **보고서 이미지** — 렌더러가 PIL로 프레임에 **비율유지 fit**(cover/contain). `app.photos`에 `width·height·sort_order` 실측 저장. 유저 크롭은 add-when.

## 5. 일부러 데이터화하지 않는 것 (YAGNI · over-engineering 회피)

유연성도 비용이다. 아래는 **코드로 두는 게 맞다**:
- **검색 필터**(`_filter_sql`) — 제네릭 필터엔진 X. 필드 추가는 저빈도·코드 몇 줄.
- **보고서 슬라이드 구성** — 데이터화 X. 서식은 `R_example.pptx` 템플릿 파일 교체.
- **서술 템플릿 DB화**(`ref.narrative_templates`) — 규칙 수정이 잦아지면 그때(add-when).

> 판단 기준: **① 변경이 잦고 ② 비개발자가/무재배포로 바꿔야 하고 ③ 이력·롤백이 필요**하면 레지스트리. 아니면 코드.

## 6. 현 상태 요약 (2026-07-21)

| 축 | 유연성 | 비고 |
|---|---|---|
| enum · 산식 · 필드메타 · 오버레이 · 마스터 버전 | ✅ 구현됨 | ref 레지스트리 + EAV + 뷰스왑 |
| 크레딧 비용 | ❌→설계 | §3.1 `ref.credit_costs` 이관 필요 |
| 보고서 서술 | ❌→설계 | §4 narrate seam |
| 보고서 이미지 | ❌→설계 | §4 auto-fit + photos 메타 |

→ 원칙은 데이터층에 잘 구현됨. **크레딧·보고서 3축만 이 원칙으로 끌어오면 전 축이 정합**된다. 실행 계획 = 리빌드 계획 Track 2 §2d.
