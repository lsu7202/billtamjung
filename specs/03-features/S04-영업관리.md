# S04 영업관리 — 매도자 · 매물 · 매수자 · 제안

> 설계 2026-08-09. 근거 = 현장 중개사가 실제로 쓰던 매수자 관리 엑셀.
> 3번째 탭 신설 — `[매물 검색] [영업] [마이페이지]`
>
> **목표는 새 기능이 아니라 연결이다.** 지금 우리 기능은 대부분 막다른 길이다.
> 매수자·제안은 그 길들을 잇는 접착제다.

---

## 1 · 문제 — 기능이 서로 모른다

| 기능 | 만들고 나면 | 끊긴 지점 |
|---|---|---|
| 검색 필터 저장 | 저장되고 끝 | 새 매물이 걸려도 모른다 |
| 브리핑 자료 | 만들고 끝 | **누구에게 보냈는지 시스템이 모른다** |
| 분석리포트 | 만들고 끝 | 협의에 어떻게 쓰였는지 모른다 |
| 내 매물 등록 | 등록되고 끝 | 다음 행동이 없다 |
| ~~업무탭(등급·명도·용도변경·긴급도)~~ | ~~입력해도 아무 데도 안 쓰인다~~ | **해결** — 매칭 엔진이 검색과 같아서 매수자 조건에 걸면 그대로 쓰인다 |

현장 엑셀을 뜯어보면 중개사는 이 끊긴 자리를 손으로 잇고 있다.
매물의 토지면적·가격·수익률·평당·명도·용도변경·보증금을 **매수자별로 다시 옮겨 적는다.**
전부 우리 DB에 있는 값이다.

---

## 2 · 원칙 — 한 번 넣은 값이 끝까지 흐른다

```
   매수자 조건을 한 번 넣으면
        ├─▶ 검색 화면에서   그 조건으로 지도를 본다 (조건 편집도 여기서 — 그리기가 되니까)
        └─▶ 매물 상세에서   「이 매물, 누구에게?」로 되돌아온다 (역방향)

   매물을 내 매물로 등록하고 업무탭을 채우면
        ├─▶ 매칭 조건으로 실제 쓰인다 (명도·용도변경·등급)
        └─▶ 자료 준비 상태(사진·브리핑·리포트)가 저절로 보인다

   브리핑 자료를 만들면
        └─▶ 「누구에게 보낼지」를 고르는 순간 제안이 생긴다
             └─▶ 보드에 뜨고, 매물 상세에도 진행 상황으로 뜬다
```

**입력을 한 번만 받고, 그 값이 다른 화면을 움직이게 한다.** 이것이 이 설계의 전부다.

업무탭(명도·용도변경·등급·긴급도)도 마찬가지다. 매칭 엔진이 검색과 같은 한 벌이라
매수자 조건에 「명도 가능」을 걸면 **입력해 둔 업무탭 값이 그대로 쓰인다.** 따로 연결할 것이 없다.

> 단, **시스템이 매물을 골라주지는 않는다.** 조건은 후보를 좁히는 도구지 판단이 아니다.
> "이 사람에게 돌릴 만한가"는 지도·주변 실거래·수익률을 사람이 보고 정한다(§8.1).

## 3 · 객체 모델 — 4개 추가

```
app.listings ──┐                        ┌── app.buyers ── app.buyer_conditions
 (매도/매물)    │                        │    (사람)          (조건 세트 N개)
 이미 있음      └──── app.proposals ─────┘
                    (매수자 × 매물)
                    app.contacts   (매수자·매도자 공용 접촉이력)
```

### 3.1 `app.buyers` · `app.buyer_conditions`
`buyers` = 사람 — `name` · `phone` · **`grade`** · **`source`** · `is_corp` · `status` · `memo`

`grade`·`source`는 **`ref.enums` + 칩**이다(`buyer_grade` / `buyer_source`, 0037).
자유입력이면 사람마다 다르게 적어 집계가 안 되고, 무엇보다 시스템의 다른 선택형 필드가
전부 칩인데 여기만 텍스트면 일관성이 깨진다.

`buyer_conditions` = **조건 세트 N개**. 한 사람이 "종로 수익형 100~200억"과
"강남 신축부지"를 같이 들고 다닌다. 조건 하나로는 현장이 안 담긴다.

**`conditions_json`은 `saved_searches.conditions_json`과 같은 모양이다.** 이 설계의 핵심.
`{values, regions, polygon, filters}` — values/regions는 재편집용 원본, filters는 엔진 입력.
매칭 엔진 = 지금 쓰는 검색(S01). 규칙이 한 벌이라 **"검색 결과"와 "매칭 결과"가 어긋날 수 없다.**

> **함정**: 모달이 저장하는 `filters`는 값 없는 키까지 전부 담는다(null 범벅).
> 그대로 두면 "조건 없음"이 truthy로 통과해 그 매수자가 **모든 매물에 걸린다.**
> null·빈배열·빈문자를 걸러낸 뒤 판단한다.

### 3.2 `app.proposals`
`buyer_id` · `building_pk` · `status`(§4) · `proposed_on` · `propose_count` ·
`channel`(브리핑/전화/문자/방문) · `report_id` · `reject_reason`(§5) · `reject_reason_sub` ·
`reject_price` · `note`

**`UNIQUE (team_id, buyer_id, building_pk)`** — 엑셀에서 색칠로 관리하던 중복 제안을 구조로 막는다.
재제안은 새 행이 아니라 `proposed_on` 갱신 + `propose_count` 증가.

`report_id`가 브리핑과 제안을 잇는다. **브리핑을 만들고 보낼 대상을 고르면 제안이 생긴다** —
따로 기록하는 일이 없다.

### 3.3 `app.contacts`
`target_type`(buyer/listing) · `target_id` · `kind`(전화·문자·방문·메일) · `occurred_on` · `note` · `created_by`

매도자·매수자 접촉을 한 표에. 어느 쪽이든 "마지막으로 언제 연락했나"가 나온다.

## 4 · 상태 5단계 *(확정 2026-08-09)*

```
후보 ──▶ 제안 ──▶ 관심 ──▶ 계약
  └────────┴────────┴──▶ 거절
```

| 상태 | 뜻 | 어디서 생기나 |
|---|---|---|
| **후보** | 골라뒀지만 **아직 안 보냄** | 매칭 목록에서 담기 |
| **제안** | 보냄 | **브리핑 발송 시 자동** · 수동 전환 |
| **관심** | 긍정 반응 | 사람이 전환 |
| **거절** | 어느 단계에서든 | 사유 필수(§5) |
| **계약** | 계약 진행 | |

`후보`가 따로 있어야 "골라는 뒀는데 아직 안 돌린 것"이 안 샌다. 보드 첫 열 = 오늘 할 일.

---

## 5 · 거절 사유 *(확정 2026-08-09)*

주 사유 1개 필수 + 부가 사유 다중 + 메모.

`price`(가격, `reject_price` 같이) · `roi`(수익률) · `location`(위치·입지) ·
`condition`(건물 상태) · `size`(규모) · `meongdo`(명도) · `tenant`(임차 구성) ·
`use`(용도·규제) · **`buyer_side`(매수자 사정 — 자금·시기)** · `etc`(기타, 메모 필수)

> **`buyer_side`를 반드시 분리한다.** 매물 탓 거절과 매수자 사정 거절을 한 통에 담으면
> 어떤 집계를 내든 거짓이 된다.

사유를 20개로 늘리지 않는 이유 — 선택지가 많으면 사람마다 다르게 고르고 `기타`로 몰린다.
집계가 목적인 필드는 **카테고리가 적고 겹치지 않아야** 한다. 세부는 메모.

## 6 · 조건에 안 담기는 것

엑셀의 자유서술(`식당 임차X`, `학원·병의원 선호`, `이면도로X`)은 필터 스키마에 안 들어간다.
**`memo`에 남기되 매칭에는 안 건다.** 안 걸리는 조건을 걸린 척하면 안 된다.

임차 업종은 층별 용도 데이터가 있어 나중에 조건화 가능 — 지금은 사람이 보는 메모다.

## 8 · 화면과 흐름  *(2026-08-09 재설계)*

```
[매물 검색]  [영업]  [마이페이지]
```

### 8.1 영업 탭에서는 매물을 고르지 않는다

처음엔 매수자 조건으로 매물을 목록으로 뿌리고 「후보로」 담게 만들었다. **틀렸다.**
그러면 "이 사람에게 돌릴 만한가"를 필터 한 번으로 정하는 셈이 된다.

실제 판단은 이렇게 나온다 —
**지도**(위치·입지) → **선택 카드**(주변 실거래로 시세 가늠) → **상세보기**(수익률·건물상태·규제).
목록 한 장으로 끝날 일이 아니다.

그래서 영업 탭은 **매수자와 제안만** 다룬다.

| 화면 | 하는 일 |
|---|---|
| 제안 보드 | 열 = 상태 5단계. 첫 열(후보) = 오늘 할 일 |
| 매수자 | 사람·등급·유입(칩) · 조건 세트 관리 |

### 8.2 조건 편집은 검색 화면에서 한다

매수자 조건 행의 「지도에서 열기」 → **검색 화면이 그 조건을 싣고 열린다.**
지도·필터·**영역 그리기**로 다듬고 상단 바에서 그 자리에 되저장한다.

조건 모달만 띄우면 **지도가 없어 「영역 그리기」를 쓸 수 없다.** 게다가 조건을 잡는 일 자체가
지도를 보면서 하는 일이다.

### 8.3 담는 자리는 매물 상세 — 「매수자」 탭

사이드바 업무 탭 옆. 매물을 받으면 첫 질문이 "누구한테 돌리지"다.

**조건 O/X만 내면 그건 필터지 추천이 아니다.** 왜 맞는지·무엇이 걸리는지를 같이 낸다.
```
김투자  A                          [후보로]
종로 100~200억
  ✓ 매매가        100억~200억 · 이 매물 140억

── 조건 밖 2명 보기 ──
박수익  B                          [후보로]
  ✗ 수익률        3.0% · 이 매물 2.52%
  지난 거절 가격 2
```

- **조건 밖 매수자도 접어서 둔다.** 조건은 참고지 규칙이 아니고,
  "조건엔 없지만 이건 보여줄 만하다"가 현장에서 자주 일어난다.
- **과거 거절 패턴**은 우리만 가진 재료다. "가격에서 두 번 막혔다"가 보이면
  같은 가격대를 또 들이밀지 않는다. `buyer_side`(매수자 사정)는 뺀다 — 매물 탓이 아니다.
- 점수 하나로 뭉개지 않는다. **"수익률만 0.48%p 모자란다"**가 보여야 판단이 선다.

### 8.4 브리핑을 보내면 제안이 생긴다

브리핑 만들기 모달에서 **「보낼 매수자」**를 고르면 생성 완료 시 제안(`제안`·채널 `브리핑`)이
자동으로 기록되고 `report_id`로 브리핑과 이어진다. 만들고 나서 따로 적는 일이 없다.
지금까지는 브리핑을 만들고 나면 시스템이 그 뒤를 몰랐다(§1).

후보 목록은 매물 상세 「매수자」 탭과 같은 추천을 쓴다 — 조건에 걸린 사람에 `조건` 표시,
이미 제안한 사람에 그 상태 표시.

### 8.4b 접촉 이력

매수자 펼침에 조건 세트와 나란히 둔다. 전화·문자·방문·메일 + 메모 한 줄.
`app.contacts`는 매도자(listing) 쪽과 같은 표다 — "마지막으로 언제 연락했나"가 안 보이면
매수자 관리가 결국 수첩으로 돌아간다.

### 8.5 흐름 한 줄

```
영업: 매수자 등록 → 조건 「지도에서 열기」
   → 검색: 지도·필터·그리기로 조건 확정 → 되저장
   → 검색/지도에서 매물 훑기 → 선택 카드(주변 실거래) → 상세보기
   → 상세 「매수자」 탭: 근거 보고 「후보로」
     (또는 브리핑 만들 때 「보낼 매수자」를 골라 바로 제안)
   → 영업: 제안 보드에서 제안 → 관심 → 거절(사유)/계약
```

## 9 · 기존 기능과의 연결

| 업무 단계 | 이미 있는 것 | 새로 붙는 것 |
|---|---|---|
| 매물 접수 | 내 매물 등록 · 업무탭(S02) | 접촉 이력 |
| 자료 준비 | 사진 · 브리핑 · 분석리포트 | 준비 상태 자동 표시 |
| 매수자 찾기 | **검색 필터(S01b)·지도** | 조건 = 같은 스키마 · 검색 화면에서 편집 |
| 제안 · 발송 | 브리핑 자료 | **만들 때 보낼 매수자 선택 → 제안 자동 생성**(report_id 연결) |
| 반응 · 협의 | 가격 3층(적정가/매매가/희망가) | 거절 사유 |

엑셀이 손으로 적던 열은 `building_pk` 하나로 전부 자동 — **입력이 사라지는 것이 1차 가치.**

## 11 · 미결 — 상의 필요

- **매도자 협상 자료**(거절 사유를 매도자에게 보여주는 화면).
  아이디어로 냈다가 내렸다. **중개사가 매도자에게 그런 자료를 실제로 내밀고 싶어하는지,
  관계상 그게 가능한지 확인되지 않았다.** 우리 추측이다.
  `reject_reason`·`reject_price`는 어차피 받으므로 재료는 쌓인다 — 필요해지면 그때 만든다.
- **조건 현실성 진단**(조건을 풀었을 때 후보가 몇 건이 되는지).
  같은 이유로 보류. 첫 상담에서 쓸모 있을 것 같지만 확인 안 됐다.
- 매수자 상세에서 브리핑을 바로 보낼지, 매물 쪽에서만 보낼지.

## 11b · 다른 기능과 어긋나지 않게 — 지켜야 할 규칙

영업만 따로 만들면 앱의 기존 규칙과 어긋난다. 실제로 어긋났던 것들이라 목록으로 남긴다.

| 규칙 | 정본 | S04에서 |
|---|---|---|
| 전화번호 자동 하이픈 | `KV.formatPhone` | 매수자 연락처 — 입력·표시 모두 통과 |
| 금액 파서 | `KV.parseAmount` | 거절 「얼마면 하겠다」 |
| 날짜 | 8자리 → ISO 저장 · `YYYY/MM/DD` 표시 | 접촉 이력 `occurred_on` |
| 면적 단위 | **`useUnit()` 전역**(브라우저 저장) | 보드 카드 대지·연면적 |
| 선택형 | `ref.enums` + 칩 | 등급 · 유입경로 |
| 파괴적 행위 | `confirm()` | 조건 삭제 |
| 저장 실패 | 사유를 화면에 | 상태 이동 · 담당자 지정 · 접촉 기록 |
| 개인정보 | 담당자+대표만 · 읽기=쓰기 경계 | 매수자 연락처 |

> **면적 단위는 화면마다 두지 않는다.** 예전엔 매물 상세에만 있는 로컬 상태라
> 상세에서 ㎡로 보다가 영업으로 넘어오면 평이 됐다. 사람의 취향이지 화면의 속성이 아니다.
> `shared/hooks/useUnit.ts`로 빼서 브라우저에 저장하고 앱 전체가 같은 값을 본다.
> (검색 필터 모달은 라벨 체계가 「평/㎡」로 따로 있어 아직 안 묶었다 — S01b 정리 때 함께.)

### 눌렀을 때 갈 곳이 있어야 한다

| 누르면 | 간다 |
|---|---|
| 보드 카드 주소 | 매물 상세(새 탭) |
| 보드 카드 매수자 이름 | 매수자 탭 + 그 사람 펼침 |
| 매물 상세 「매수자」 탭의 이름 | `/sales?buyer=N` |
| 조건 「지도에서 열기」 | 검색 화면(조건 실림) |

### 삭제는 흔적을 남기지 않는다

매수자 소프트 삭제 시 **조건 세트와 보드 카드도 함께 사라진다.**
예전엔 `list_proposals`가 `deleted_at`을 안 걸러서, 사람은 목록에서 사라졌는데
그 사람 카드만 보드에 남아 눌러도 갈 곳이 없었다.
