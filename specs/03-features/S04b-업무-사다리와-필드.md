## 0. 경위와 **표본의 한계**

현장 중개사무소의 실제 업무 엑셀(`docs/자료/중개인업무자료.xlsx`, 35시트)을 전수 분석해
업무 중 발생하는 상황을 뽑고, 우리 필드와 대조한 결과다.

> **⚠ 표본은 하나다.**
> 이 엑셀과 [[중개사피드백-2026-07~08]]은 **같은 사무소에서 나왔을 가능성이 높다**
> (피드백 실측 대상 `종로2가 71-6`이 엑셀에 전용 시트 `종로2가 71-6 꼭 매각하자`로 있고,
> 엑셀 안에 「빌탐정 V1 분석보고서 개발 설명서 초안」이 들어 있다 — 이 사무소는 설계 파트너다).
> 엑셀의 `공동중개` 2,861행에 다른 중개사무소가 나오지만 **거래 상대의 연락처와 회신**일 뿐,
> 그 사무소들이 어떻게 일하는지는 한 줄도 없다.
>
> 따라서 **이 문서의 관찰은 「중개 업무 일반」이 아니라 「한 사무소의 방식」**이다.
> 다른 사무소 자료를 얻기 어려우므로, §1의 기준으로 노이즈를 걷어내고 쓴다.
> **「공통이다」라고 쓰려면 근거를 댄다.**

### 1.2 특히 단단한 근거 둘

**④ 만들려다 실패한 자리** — 우리가 하면 바로 값이 난다.
- `9_1`에 **「결과 추후 재시작 요일」 컬럼을 팠는데 값이 한 줄도 없다** → **멈춤의 깨우는 조건**(§2.3)

**③ 본인이 규칙으로 못 박은 것**
- `매물찾을때 그전에 찾았던건지 검색해보기` / `버릴거라도 빨간색으로 바꾸고 지우지 않기(지우면 새로운 건 줄알고 다시 분석해 보게됨)` → **제외**(§3.1)

## 2. [규칙] 뼈대 — 사다리 셋 + 멈춤 하나

```
① 매물     발굴 → 소유자 확보 → 접촉 → 의사 확인 → 정보 → 자료 → 【살 사람 찾는 중】
② 매수자   확보 → 접촉 → 조건 → 【살 물건 찾는 중】
                          ↓  ①끝과 ②끝이 만나면 선다
③ 제안     후보 → 브리핑 → 임장 → 조율 → 가계약 → 계약 → 잔금 → 완료

④ 멈춤     사다리 어느 칸에서든 겹친다 — 사유 + 깨우는 조건
```

기존 상태축(후보·제안·계약·철회)은 **한 사다리에 두 개체의 일을 섞어** 담고 있었다.
매물의 「팔 준비가 됐나」와 거래의 「어디까지 갔나」는 다른 얘기다.

- 각 사다리는 **단조 증가**한다. 「어디까지 갔나」가 하나로 정해진다.
- **제안은 매칭의 결과물**이다. 매수자×매물 쌍마다 하나.

### 2.1 [규칙] 단계는 **필드에서 파생**한다

사람이 단계를 찍지 않는다. 각 단계의 「끝났다 =」가 곧 규칙이고, **빈 칸이 곧 할 일**이 된다.
상태는 늘 장부의 파생값이라는 원칙([[프로필-커밋]])과 같다.

화면에는 **읽기 전용 표시**로만 나온다. 모달에 「단계」 칸은 없다.

### 2.2 [규칙] 1:N — 대표 상태는 **가장 앞선 단계**

한 매물에 제안이 여럿일 때 매물의 거래 상태는 **가장 앞선 제안의 단계**다.
매수자 쪽 `top_status`(`backend/app/domains/buyers.py`)가 이미 쓰는 규칙을 그대로 쓴다.

```sql
ORDER BY CASE status WHEN '계약' THEN 1 WHEN '제안' THEN 2
                     WHEN '후보' THEN 3 WHEN '계약파기' THEN 4 ELSE 5 END,
         updated_at DESC
```

파기된 건이 있어도 살아 있는 건이 이긴다.

### 2.3 [규칙] **멈춤** — 어느 칸에서든 겹치는 공통 축

「실패」는 사다리 칸마다 생긴다. 그런데 뜯어보면 전부 같은 말이다:

> **지금은 못 간다 + 무엇이 있으면 다시 간다**

| 어느 칸 | 멈춤 사유 | 깨우는 조건의 예 |
|---|---|---|
| ①1 소유자 확보 | 연락처 못 캠 · 법인 담당 못 찾음 | DM 회신 · 다른 수단 |
| ①2 접촉 | 연락두절 · 통화 거부 | 6개월 뒤 |
| ①3 의사 | 안 판다 · 나중에 | `26년 봄에 매각예정` |
| ①5 자료 | 진행불가(수익률·가격·물건 자체) | 가격이 내려가면 |
| ①6 살 사람 찾기 | 맞는 매수자 없음 | 조건 맞는 손님이 생기면 |
| ②3 조건 | 자금 틀어짐 | `아파트 올해안에 정리하고` |
| ③ 어디서든 | 상대 사정 · 선행조건 · 시점 | `1/29 계약예정이라 보류중` |

**필드 6~7개가 하나(+칸별 사유 목록)로 합쳐진다.** 창도 하나로 쓴다 — 어느 칸에서 눌러도 같은 모양이고 사유 칩만 달라진다.

**깨우는 조건의 값** — 날짜만 받으면 대부분 못 적는다. 막연한 시점이 실무의 표준이다:
`26년 봄에 매각예정` · `올해중순이나 말에 전화하자` · `9월쯤?` · `연말쯤` ·
`내년초 잔금 기준으로 매수 원함` · `1/29 계약예정이라 보류중`(사건) · `좋은 매물 있으면`(조건).

```
🕐  [날짜]  또는  [올해 안][연말][내년 초][봄][가을]  또는  [조건: ___]
```

**「잠든 것」의 정의 전부가 여기서 나온다** — 깨울 때가 지난 멈춤 + 깨우는 조건 없이 오래 멈춘 것.

### 2.4 [규칙] 검토와 멈춤은 다르다

| | 검토 | 멈춤 |
|---|---|---|
| 공이 누구에게 | **상대에게** | **아무에게도 없다** |
| 깨우는 것 | 상대의 답 · 내 재촉 | 시점 · 사건 · 조건 |
| **재촉이 통하는가** | ○ | **✗** |

현재 「검토」 답글은 대시보드에 **아무 영향이 없다** — 승격 조건이 경과일뿐이라
상대가 「3월에 다시 보자」고 해도 매일 「답 없음」이라고 재촉이 뜬다.

### 2.5 [규칙] 양쪽을 잇는 길은 **양방향**

중개인마다 잘하는 게 다르다 — 매수자 확보에 강한 사람과 매물 확보에 강한 사람이 있다.
①과 ②는 **독립적으로 완결**되어야 하고, 잇는 길이 양쪽 다 있어야 한다.

| 방향 | 현재 |
|---|---|
| 매수자 → 살 물건 | ● `buyer_conditions` + 검색 |
| 매물 → 살 사람 | ✗ **역검색이 없다** |
| 매수자 조건 → 매도자 확보 | ✗ 없다 (`DM (지주작업 리스트에 업데이트함)`) |

### 2.6 [규칙] 「찾는 중」이 각 사다리의 종착이자 가장 오래 머무는 곳

```
①6 매물이 살 사람을 못 찾은 채 멈춘다   「브리핑할 매수자가 없음 상가주택이라 매수자 희소함」
②4 매수자가 맞는 물건을 못 찾고 멈춘다   「한동안 알아보다가 마땅한 곳 없어서 보류중」
```

진행 중도 아니고 끝난 것도 아니라 **어느 화면에도 안 뜬다.** 「까먹은 것」의 대부분이 여기 있다.

## 3. ① 매물 사다리

| 단계 | 끝났다 = | 새 필드 | 기준 |
|---|---|---|---|
| **0 발굴** | 목록에 담김 | **제외 + 사유** | ③ |
| **1 소유자 확보** | 이름 + 전화가 있다 | — | |
| **2 접촉** | 한 번이라도 말이 됐다 | **통화 결과** | ①③ |
| **3 의사 확인** | **원함**을 들었다(검토=진행 · 거절=정지) | **매도 시기**(0099 — 원함인 채의 정보) · **매수도 원함**(0098 전환) | ①③ |
| **4 정보** | 물어봐야 아는 셋의 **답을 안다**(확인중=진행) | **확인 상태**(값 추가) · **임대내역 확인 상태**(0100) | ① |
| **5 자료** | 사진 + 빌탐정 리포트가 있다 | — (종류별 매칭은 파생) | |
| **6 살 사람 찾는 중** | 바깥에 나가 있다(광고 **또는 공동중개** 또는 제안) | **광고 상태** · **공동중개 발송**(0098) | ① |

**옆문** — 철회 · **타사 계약**(`master.sales_history` 실거래로 자동 감지) · 연락두절(멈춤)

### 3.1 [규칙] 제외는 **삭제가 아니라 접기**

> `버릴거라도 빨간색으로 바꾸고 지우지 않기(지우면 새로운 건 줄알고 다시 분석해 보게됨)`

```
검색 결과 10건
├─ 안 본 것 6건          위에, 평소처럼
└─ [이미 본 것 4건 ▸]    접힌 채로 맨 아래, 회색 — 펼치면 사유와 본 날짜
```

조건을 완화해 다시 검색해도 위로 안 올라오고, 영영 사라지지도 않는다.

- **범위는 전역**(내 계정). 현장 요청이 명시적이다 — 「매수자별이 아니라 전역 적용」 + 간단 메모.
- **검색 화면(S01)의 일이다.** 모달과 겹치지 않아 분리해 진행한다.
- [미정] 시간이 지나면 다시 올라오는가. 기간을 두는 것 자체가 자의적이다.

### 3.2 [규칙] 연락처 캐는 **수단은 문장으로, 상태는 구조로**

수단(구글링·대장·임대문의·DM·정화조·온하우스)을 칩으로 고정하지 않는다 — 기준 ⑤.
필요한 것은 수단이 아니라 **「지금 기다리는 중인가」**인데, 그건 멈춤이 담는다.

```
아직 아무것도 안 함   소유자 커밋이 0건               → 파생
시도했는데 진행 중     커밋은 있는데 전화가 없음        → 파생
회신 대기             멈춤 · 깨우는 조건 = DM 회신     → 멈춤
결국 못 캠            멈춤 · 사유 = 연락처 못 캠      → 멈춤
```

수단 이름은 커밋 문장에 남는다(`대장 떼봤는데 없음`). 집계는 안 되지만 집계할 이유가 없다.
나중에 필요하면 **커밋 입력줄에 칩 한 줄**을 붙이면 되므로 되돌리기 쉽다.

### 3.3 [규칙] 정보는 두 종류다 — 측정이 잡아낸 오류

```
임대내역 있음   3,065건   ← 연락처 있는 것(2,206)보다 많다
```

**소유자와 통화한 적 없는 건물의 임대내역을 이미 알고 있다.** 광고·현장에서 얻기 때문이다.
명도(1,175) · 용도변경(886) · 멸실(619)은 전부 연락처(2,206)보다 작다.

```
밖에서 얻는 것    임대내역 · 컨디션 · 입지 · 광고 여부   ← 접촉 전에도 안다. 단계 판정에서 제외
물어봐야 아는 것  명도 · 용도변경 · 멸실                ← 접촉 후에만. 단계 4의 판정 조건
```

단계를 늘리지 않는다(관문이 아니다). **단계 4의 끝 조건에서 임대내역을 뺀다.**

### 3.4 [규칙] 「확인 상태」는 **값으로** 넣는다

우리 필드는 값은 갖췄는데 `확인중`이 없다. 엑셀은 값으로 넣었다 —
명도 확인중 87 · 멸실 확인중 339 · 용도변경 확인중 62.

```
명도       미지정 · [확인중] · 완료 · 가능 · 불가 · 일부 · 조건부
멸실       미지정 · [확인중] · 불가 · 협조가능 · 잔금전멸실 · 나대지 · 협의가능 · 조건부
용도변경   미지정 · [확인중] · 나대지 · 근생 · 상가주택 · … · 가능 · 불가 · 협의가능 · 조건부
```

```
미지정  = 아직 안 물어봤다   →  「물어봐야 할 것」으로 뜬다
확인중  = 물어봤는데 모른다   →  안 뜬다. 소유자도 모르는 걸 재촉할 순 없다
```

이 구분이 없으면 대시보드가 **소유자도 모르는 걸 계속 재촉**한다.
**「미지정」과 「확인중」은 칩에서 나란히** 둔다 — 붙어 있어야 뜻이 대비로 읽힌다.

### 3.5 [규칙] 광고 상태는 **경쟁 정보**다

우리가 광고를 올리지 않아도 필요하다.

```
광고 중      다른 중개사도 이 물건을 안다 = 경쟁이 있다
광고 안 됨   나만 아는 물건 = 가치가 높다
광고 불가    소유자가 노출을 원치 않는다 = 조용히 팔아야 한다
```

`광고없음,광고불가능`이 228건으로 가장 많았던 이유 — **「우리만 아는 물건」을 세는 칸**이었다.
내린 사유 중 `매각됨`은 실거래로 자동 감지하므로 우리가 채운다.

## 5. ③ 제안 사다리

### 5.1 [데이터] `side` — 협상은 양쪽이 오간다

현재 제안 장부는 **한쪽만** 만들어져 있다.

```
매수 장부(proposal_events)   price · reaction · reject_reason · reject_price · reply_to_event_id
매도 장부(contacts)          status · note                    ← 가격 칸도 답 칸도 없다
```

`ask_price`를 덮어쓰면 「거절하면서 133을 불렀다」인지 「그냥 값을 내렸다」인지 구분되지 않는다.

**`proposal_events`에 `side`(매수·매도) 한 칸을 붙여** 기존 `price`·`reaction`·`reject_price`를
양쪽이 나눠 쓴다.

```
side  값       답              뜻
매도  148억                    내놓은 값
매도  140억                    조정 가능하다고 함
매수  140억                    매수자에게 제안
매수           거절 · 128억     매수자가 부른 값
매도  128억    거절 · 133억     매도자에게 물었더니 거절, 133 부름   ← 지금 없는 줄
매수  133억                    재제안
매수           수락            성사
```

- 수락·검토·거절이 **양쪽 다 성립**한다.
- **협의 폭**이 마지막 매도값 − 마지막 매수값으로 나온다.
- 협상이 **쌍에 속한다** — 한 매물에 매수자가 셋이면 매도자에게 셋을 각각 물어본다.
  `contacts`는 매물 단위라 이걸 못 담는다.
- 기존 거울(`proposal_events ↔ contacts`)이 그대로 돌아 매물 장부에도 비친다.

**갈래를 나눈다** — 제안과 무관한 매물 단위 가격 변동(「그냥 140억까지 낮추기로 하심」)은
지금처럼 `contacts` + `ask_price`로 간다.

## 7. [규칙] 모달 — 창 12개

### 7.1 필드 정의는 한 곳, 창은 「어느 키를 보여줄지」만

창이 12개가 되면 「등록 창과 편집 창의 필드가 다르다」는 버그가 12배로 벌어진다.
`PersonModal`이 이미 쓰는 방식(`ROWS` + `ENUM`)을 전체로 올린다.

```ts
const F = {                                    // 필드의 정본 — 여기 말고 어디에도 안 적는다
  meongdo:  { label:"명도", kind:"enum", enum:"meongdo", icon:KEY, on:"listing" },
  …
}
const PANE = {                                 // 창 = 줄 배열. 한 줄에 칩 여러 개
  정보: { rows:[ ["meongdo","use_change"], ["myeolsil"] ] },
  …
}
```

- **필드 추가 = `F`에 한 줄 + 창 배열에 키 하나.** 두 군데 이상 안 적는다
- 같은 필드가 두 창에 나와도 **정의가 하나라 어긋날 수 없다**
- 어법이 `kind`에서 자동 결정된다 — `enum`→칩 · `money`→클릭편집 · `when`→시기 · `text`→pill.
  **CLAUDE.md의 어법 표를 코드로 굳히는 셈이다.**

| ③ | 8 완료 | *창 없음* | 없음 |

**접촉은 창을 만들지 않는다.** 전화 끊자마자 한 줄 치는 일이라 창을 띄우면 느려진다.
커밋 입력줄에 칩 한 줄을 단다:

```
[ 방금 통화 내용… ]  [통화됨][부재][전원꺼짐][끊김][통화중][로밍][결번]
```

칩 하나만 눌러도 커밋이 서고 `마지막 접촉일`·`연속 실패`가 갱신된다.

### 7.4 필드가 많아질 때를 버티는 장치 넷

1. **채움 표시** — 창 머리에 `2/3`. 사다리에도 같은 숫자
2. **안 찍은 칩은 흐리게** — 눈이 찍힌 것부터 읽는다
3. **구분선으로 묶기** — `gm-sep`(이미 있음). 정보 창은 「물어서 아는 것 / 밖에서 아는 것」으로 나눈다
4. **표는 창을 따로** — 층별 임대내역처럼 행이 여럿인 건 줄에서 `3개 ▸`로 접는다

### 7.5 [규칙] 창을 저장하면 장부에 **한 줄로 묶여** 남는다

필드를 하나 고칠 때마다 커밋을 세우면 장부가 기계 줄로 넘친다.
**창 단위로 묶어 한 줄**을 남기고, 그 줄은 `auto`로 접힌다.

```
찍는다:  명도 = 가능 · 용도변경 = 근생
장부:    「명도·용도변경 확인」   ← auto, 접힘
```

사람이 쓴 문장만 펼쳐져 보인다. 지금 거울 줄에 쓰는 `auto` 플래그가 그 역할을 한다.

## 8. 측정 — 어느 칸에 물량이 몰리나

`1.찐(서울)` 7,683건 기준.

1,677  ( 21.8%)  2 접촉 — 누구와 말했는지 안다     ↓   529
1,175  ( 15.3%)  4 정보 — 명도를 안다
  886  ( 11.5%)  4 정보 — 용도변경을 안다
  619  (  8.1%)  4 정보 — 멸실을 안다
  160  (  2.1%)  5 자료 — 사진 있음
  125  (  1.6%)  5 자료 — 브리핑함

> 「관리 대상으로 올림」(512)을 의사 확인의 대리 지표로 썼다가 임대내역(3,065)보다 작게 나와
> **대리 지표가 나빴다는 게 드러났다.** 절대 수치가 아니라 **칸 사이의 낙차**만 유효하다.

**물량과 우리 기여도는 다르다.**

| 단계 | 막힌 물량 | 우리가 할 수 있는 것 |
|---|---|---|
| 소유자 확보 | **5,477** | 순서를 매긴다(`sell_score`) · 어디까지 해봤나 기록 |
| 접촉 | 529 | 결과 기록 · 재시도 시점 |
| 정보(물어봐야) | 1,031 | 「뭘 아직 안 물어봤나」 표시 |
| 자료 | 1,015 | **보고서를 자동 생성** ← 값을 직접 채우는 유일한 곳 |

### 8.1 만드는 순서 = **단계 순서**

물량이나 기여도로 정하지 않는다. 사다리 순서대로 만든다 —
앞 칸이 안 서면 뒤 칸의 값이 안 쌓이기 때문이다.

### 8.2 [규칙] 재촉은 유한한 창에서만 (2026-08-18)

「N일째 움직임 없음」 카운트를 **무한정 올리며 매일 띄우지 않는다** — 무시하기로 한 건이
1년 내내 뜨면 재촉 자체를 안 보게 된다(늑대 소년). 규칙:

```
움직임 끊김 D+4 ~ D+7   대시보드가 재촉한다 — 「4일째 움직임 없음」 … 「7일째」
D+7 이후                재촉을 멈추고 **잠든 것** 목록으로 넘어간다(원할 때 보는 곳)
```

- 임계(7일)는 화면 규칙일 뿐 저장되지 않는다 — 저장되는 건 마지막 움직임 날짜(파생)
- 재촉 주기는 「연락할 차례」의 재통화 상수(RECALL_DAYS)와 맞춘다 — 색 전환과 재촉이 같은 말을 하게
- 진행 표시(노랑) = 최근 7일 내 움직임. 수동 [진행] 선언은 「소유자 찾기 진행」 커밋으로 남는다
  (새 필드 없음 — 선언도 장부의 사실이다)

### 10.4 [규칙] 상태 칩 — 초록은 고를 수 없다 (2026-08-18 확정)

```
칩 클릭 순환   회색(시작 전) → 노랑(진행 중) → 빨강(정지) → 회색
초록(완료)     값이 만든다. 고를 수 없고, 초록인 칩은 눌리지 않는다(값을 지워야 내려간다)
우선순위       값(파생) > 내가 고른 상태 — 값이 초록을 만들면 이전 선언은 무시된다
```

셋은 전부 **내 의사**라 선언이 곧 사실이지만, 완료는 **사실의 문제**다. 값 없이 초록을
허용하면 초록이 두 뜻(값이 있다 / 내가 눌렀다)을 갖고, ① 대시보드가 할 일을 숨기고
② §8 깔때기 측정이 오염되며 ③ 그 초록을 본 팀원이 없는 근거를 믿고 움직인다.
그래서 **강제 완료(0103)는 0105로 폐기**했다.

되돌리는 경우는 셋인데 전부 값으로 풀린다 — 실수=값을 지운다 · 상황 변화=새 사실을
기록한다(값 갱신+커밋) · 무산=정지(빨강). 별도의 되돌리기 장치는 두지 않는다.
값이 없는데 진행해야 하는 일이 잦으면 그건 **필드가 현실을 못 담는다는 신호**다.

### 10.5 [규칙] 되돌리기는 **값 취소** 하나다 (2026-08-18 전수 확인)

모든 칸이 같은 방식이다 — 창의 **값**이 초록을 만들고, 그 값을 취소하면 내려간다.

| 칸 | 초록을 만드는 값 | 되돌리는 손동작 |
|---|---|---|
| 소유자 | 이름 + 전화 | 전화 비우고 저장 |
| 접촉 | 통화 결과(통화됨) | 칩 재클릭 |
| 의사 | 매도 의사(원함) | 칩 재클릭 |
| 정보 | 명도·용도변경·멸실의 **답** | 칩 재클릭(그 칸만 내려감) |
| 매칭 | 살아있는 쌍 | 쌍 옆 × |
| 브리핑 | **방식**(자료 발송·만나서·전화·현장에서 · 0107) | 칩 재클릭 |
| 임장 | **다녀옴** | 칩 재클릭 |
| 가계약·잔금 | 날짜·금액(하나뿐인 사실) | 날짜 × · 금액 비우기 |

- **자동 줄은 못 지운다** — 장부의 「브리핑 기록」류는 값의 **그림자**다. 그림자만 지우면
  값이 남아 상태가 안 내려가서(사용자가 고장으로 읽는다) 삭제를 잠갔다. 사람이 친 메모는 자유.
- 브리핑·임장이 여러 번인 것은 **장부의 여러 줄**이 말한다. 값은 「했다」는 사실 하나다.

### 10.6 [규칙] 거래 칸은 **일정이 정본** (2026-08-18)

```
브리핑   방식(칩) = 했다 · 약속 줄 = [약속 잡기] → 예정 → [했다고 표시] → 완료
계약·잔금 창이 날짜를 따로 갖지 않는다 — 캘린더의 그 약속이 곧 이 칸의 날짜다
임장     **칸이 아니다**(자료·노출과 같은 이유) — 갔다·안 갔다는 체크리스트다.
         안 보고 사기도 하고 열 번 보고 안 사기도 한다. d3_visit 은 표시용으로만 남는다
```

창이 제 날짜를 들고 있으면 캘린더와 두 벌이 되어 **반드시 어긋난다**(어제 옮긴 약속이
창에는 옛 날짜로 남는다). 그래서 거래 칸의 날짜는 `app.schedules` 를 읽고 쓴다 —
칸별 요약(`cell_sched`: 예정 due_on · 완료 done_on)을 서버가 파생으로 내려준다.

> **거울로 잇는다**(2026-08-18) — 약속은 별도 창을 띄우지 않고 창의 「약속」 줄에서
> 바로 잡고 옮긴다. 그 줄과 캘린더는 **같은 약속**이다: 여기서 날짜를 고치면 일정이
> 옮겨가고, 캘린더에서 끌어 옮기면 여기 그대로 보인다(커밋↔일정 거울과 같은 규칙).
> 종류는 칸이 정한다(브리핑 칸에서 계약을 고를 일이 없어 토글을 감춘다).
>
> **서류는 계약·잔금 칸의 것**이다. 같은 쿼리 키의 캐시가 다른 칸 창에 새어
> 브리핑에 잔금 서류가 뜨던 버그를 칸으로 가둬 막았다.

### 10.7 [규칙] 값과 말을 가른다 — 창에서 커밋을 뺐다 (2026-08-18 확정)

```
값(필드) = 상태.  창이 다룬다        → 칩 · 입력 · 체크리스트 · 정지 사유
말(커밋) = 맥락.  카드·대화창이 다룬다 → 사람이 친 문장 + 제안 왕복(가격·답)
```

- **창에 기록 탭·입력줄이 없다.** 창이 절반으로 줄고, 「창의 커밋은 그 창의 것」·그림자
  삭제 잠금·칸별 kind 태깅·「시작 전」 표식 줄이 **전부 사라졌다**.
- **값 저장은 장부에 줄을 안 남긴다.** 「소유자 확보 · 이름」·「브리핑 기록」·「되돌림 · …」·
  정지/재개 줄을 폐기했다 — 값이 이미 그 사실이라 그림자가 오해만 만들었다
  (「이게 상태인가?」 · 「기록 지웠는데 왜 안 돌아가?」의 원인).
- **노랑의 뜻이 바뀌었다** — 「최근 커밋」이 아니라 **부분 채움**이다: 정보 1/3 · 이름만 알고
  전화는 모름 · 급함만 찍힘 · 방식만 골라둠. 값만으로 계산되고 뜻이 더 정확하다.
  회색=아무것도 없음 · 노랑=하다 만 것 · 초록=됨 · 빨강=정지.
- 잃는 것은 「누가 언제 이 값을 바꿨나」의 감사 이력이다. 베타에선 값과 대화창 기록으로
  충분하고, 필요해지면 별도 이력 테이블로 붙인다(화면에 섞지 않는다).

### 10.8 [규칙] 매칭 창 = 쌍 하나를 통째로 (2026-08-19)

브리핑·조율·임장을 **매칭 안으로 접었다** — 「담고 → 보여주고 → 값이 오가고 → 맞는다」는
한 흐름이고 상대가 같은 사람이라, 칸으로 쪼개면 같은 사람을 세 번 열게 된다.

```
매수자 탭  붙은 사람들(합의된 쌍엔 초록 점) · [＋ 담기]
브리핑     방식 칩(자료 발송·만나서·전화·현장에서)
일정       이 매물의 약속들이 보이고 ✓로 완료 · [일정 만들기]가 일정 창을 연다
가격       매수희망 · 합의가 · [매도|매수] 값 부르기 → 오간 값이 순서대로 쌓인다
정지       창 맨 아래 한 구획(탭이 아니다)
```

- **레일은 9칸** — 소유자·접촉·의사·정보·**매칭** + 가계약·계약·잔금·신고.
  매칭 다음은 곧 계약 절차다.
- **매칭의 초록 = 합의된 쌍이 있다**(수락 답 또는 합의가) — 「나 이거 살래/팔래」가 맞은 순간이
  진짜 매칭이다. 담기만 한 것은 노랑(오가는 중).
- **호가판 탭** — 이 매물의 값이 한 판에: 매매가 · 매도희망 + **모든 매수자의 희망가**가
  한 줄씩, 각 줄에 매도희망과의 차이. 사람 줄 아래에 **누가 언제 얼마를 불렀는지**가
  시간순으로 붙는다(매도=보라 · 매수=파랑). 「저번에 145까지 갔었지」가 다음 수를 정한다.
- 값은 클릭-편집이다 — 「부르기」 같은 낱말을 두지 않는다(어느 값인지는 라벨이 말한다).
  저장된 값이 곧 기록이라 이력을 따로 적지 않는다(제안 장부에서 파생).

> **매칭 창 배치 확정(2026-08-19)** — 탭 줄엔 **참여자만** 선다:
> `[매도자] [매수자들…] ＋ ⋯ [호가판]`. 매도자 탭이 매매가·매도희망·최고 제시(갭)를 들고
> 있어 매수자가 여럿이어도 매도 쪽 값은 한 자리다. **담기는 탭이 아니라 ＋ 동작**(누르면
> 탭 줄 아래 인라인 검색 한 줄), **빼기는 그 사람 탭의 ×**(hover 때만). 호가판은 오른쪽 끝.
>
> **호가판은 표다** — 행=참여자 · 열=값이 움직인 날 · 칸=값. 안 움직인 날은 빈칸이라
> 움직임이 모양으로 읽힌다. 오른쪽 끝에 지금 값과 갭. 그래프는 폐기(읽기 어려웠다).
> 값 이력은 `app.field_events`(0109)에 쌓는다 — 덮어쓰지 않는다(조사 규범).

> **브리핑은 한 줄기다(2026-08-19 · 0111)** — 「할 일(약속) → 한 일(방식)」이 같은 줄에서 흐른다:
> ① 비어 있으면 **「브리핑 일정 만들기」** ② 일정 창에서 종류=브리핑을 고르면 **방식**(만나서·전화·
> 자료 발송)이 따라 뜨고, 저장하면 브리핑 자리에 **약속 카드**(8/22 만나서 예정 · [했다])가 선다
> ③ 「했다」를 누르면 카드가 사라지고 **그 방식이 브리핑 값**으로 켜진다. 방식은 **여럿일 수 있다**
> (0110 — 자료 보내고 나중에 만나서 또 한다). 「현장에서」는 「만나서」와 같은 뜻이라 폐기.
>
> 삭제는 **창 바닥 왼쪽**(저장과 같은 급, 반대편). 탭은 이름을 가리지 않는다 — 덮으면 선택이 막힌다.

> **브리핑은 칩이 본 기능이다(2026-08-19)** — 일정은 부가다. 방식 칩(만나서·전화·자료 발송)은
> 항상 서 있고 누르면 그게 곧 「했다」다. 약속을 잡아야만 완료가 되면, 이미 하고 온 브리핑을
> 기록하려고 지나간 일정을 지어내게 된다. 창에 「일정 만들기」는 하나뿐 — 「브리핑 일정 만들기」.

### 10.9 [규칙] **계약** — 「매칭」을 버렸다 (2026-08-19 · 0113~0115)

「매칭」은 부동산에서 안 쓰는 낱말이라 뜻이 안 통했다. 다섯째 칸의 이름은 **계약**이고,
그 창이 곧 계약을 짓는 자리다. 뒤쪽 거래 칸의 「계약」은 **계약서**로 고쳐 부른다 —
앞은 *누구와 얼마에*, 뒤는 *계약서를 쓴 날*이라 층이 다르다.

```
소유자 · 접촉 · 의사 · 정보 · 계약 · 잔금 · 신고
                              └ 회색 담은 매수자가 없다
                                노랑 담았다 → 상대·값을 정했다 → 계약 일정을 잡았다
                                초록 그 **계약 일정을 했다**(0116)
```

**가계약·계약서 칸은 없앴다**(0116) — 계약 칸 하나가 「누구와 · 얼마에 · 언제」를 다 안고,
서류는 그 창의 체크리스트다. 칸으로 세우면 같은 계약을 세 번 열게 된다.
잡아 둔 약속은 아직 일어난 일이 아니므로, **날짜만으로는 초록을 주지 않는다**.

**계약은 첫 탭에서 한 큐에 짓는다.** 매수자 탭은 값이 오가는 자리고, *정해지는* 자리는
하나뿐이다 — 매수자별로 흩어 두면 「그래서 누구랑 얼마에 가는 건가」를 탭을 돌며 세게 된다.

```
계약(첫 탭)   매매가 · 매도희망 · 최고 제시(상대 정하기 전에만)
              계약 상대  [이서연][김민준]     ← 칩. 고르면 그 사람의 매수희망가가 계약가로 들어온다
              계약가     142억  8/19 계약 일정 ✓   ← 값과 약속이 한 줄(얼마에·언제는 한 호흡)
              서류       매도자 신분증 · 인감도장 …  ← **계약 일정이 생긴 뒤에만** 뜬다
매수자 탭     **명함**(업무 탭과 같은 얼굴 · 레일·조건 편집·사람 편집은 뺀다) · 브리핑 · 매수희망
              계약 관련은 안 둔다 — 계약 탭에서 관리되므로 두 군데서 고칠 일이 없다
```

- **상대 → 값 → 일정**이 한 줄기다. 상대만 고르면 노랑, 계약가까지 서면 초록, 일정은 그 다음.
- **매물당 하나**. 다른 칩을 누르면 앞사람은 서버가 푼다(그 사람의 매수희망가는 남는다).
  다른 매수자를 지우지는 않는다 — 계약서 전엔 뒤집히므로 대기줄은 살려 둔다.
- **되돌리기는 칩 재클릭 하나**(창 공통 어법). 계약가도 같이 풀린다 — 그 동작이 만든 값이다.
- **계약 일정 창에 계약가가 미리 들어간다**. 거기서 고친 금액이 곧 확정가다(서버 거울) —
  값이 두 곳에 따로 살면 반드시 어긋난다.
- 약속을 소화했다는 표시는 **캘린더와 같은 체크 아이콘**이다(글자 버튼 「했다」 폐기).
- **일정을 지우면 그 일정이 실어 나르던 사실도 걷힌다**(2026-08-19). 계약 일정의 ✓ 는 곧 계약
  체결이므로, 그 일정을 지우면 계약도 없던 일이 된다(제안 status·매물 status·거울 줄까지).
  진짜 이뤄진 계약은 지울 일이 없다 — 지운다는 건 시험 삼아 또는 잘못 만들었다는 뜻인데,
  그게 「계약된 매물」로 남으면 그 뒤 모든 화면이 거짓말을 한다. 되돌리기(✓ 해제)와 **같은 길**을
  쓴다(`delete_schedule` → `schedule_set_state(예정)` → `schedule_retract`).
- **칩은 매물마다 하나뿐이다**(2026-08-19). 단계 칩 옆에 거래 배지(계약·계약파기·철회)를 또
  세우던 것을 걷었다 — 「계약(회색) · 계약(초록)」처럼 같은 말이 다른 색으로 나란히 섰다.
  계약파기·철회는 정지(빨강)로 읽는다.
- **칩 = 레일의 지금 칸**(`railNow`) — 뷰의 stage(매물 5칸까지만 아는 값)를 쓰던 탓에
  레일이 잔금까지 초록인데 칩은 「계약」에 멈춰 있었다. 이제 둘이 같은 사다리를 읽는다.
- **목록 칩과 레일은 같은 재료를 먹는다**(`stageCls`) — 전엔 레일만 부분 채움(busy)을 봐서
  같은 매물이 목록에선 회색, 레일에선 노랑이었다. 색 규칙은 하나였는데 재료가 달랐다.
- **계약 일정 창에서 중도금·잔금 날짜도 같이 잡는다**(선택 · 2026-08-19). 셋은 한 자리에서
  정해진다 — 계약서를 쓰며 「중도금 9/20, 잔금 11/5」를 같이 적는 게 실제 순서다. 비워 두면
  안 만들고, 나중에 그 일정을 열어 고치면 된다. 계약 종류가 아닌 창(잔금만 잡기 등)은 그것만 만든다.
- **계약 자리엔 매도자가 자동으로 참석자에 든다** — 도장 찍는 두 사람이 빠진 약속은 반쪽이다.
- 이미 잡힌 약속은 「만들기」가 아니라 **일정 보기**다(누르면 그 약속 창이 열린다) — 있는 것을
  두고 만들기가 서면 같은 약속이 둘 생긴다. 소화한 약속은 점이 초록으로 바뀐다.
- 브리핑 일정의 방식 기본값은 **만나서** — 비워 두면 방식 없는 약속이 남는다.
- 매수자 사다리도 같다 — `b4_match` = 상대와 값이 선 쌍이 있다 · `b4_open` = 살아있는 쌍.
