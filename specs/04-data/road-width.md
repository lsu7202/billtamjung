# 도로폭(접도) 데이터

## 왜 필요했나

중개 브리핑 자료의 「도로상황」은 `전면 25m / 측면 5m / 후면 4m`처럼 **실제 폭(m)**으로 적힌다.
그런데 우리가 가진 건축물대장의 `road_frontage`는 `광대로한면·소로각지` 같은 **분류 코드**뿐이라
폭을 알 수 없었다.

## 검토한 방법과 결과

| 방법 | 결과 |
|---|---|
| 연속지적도 도로 필지(`jimok='도로'`, 14.3만 필지)에서 면적÷길이로 추정 | ❌ 도로가 잘게 쪼개져 있어 대로변에서 크게 빗나감 — 노량진동 54-8 실제 25m를 **9.3m**로 추정 |
| 네이버 지도 API | ❌ 도로 제원 미제공(지도·로드뷰·지오코딩·길찾기만) |
| **도로명주소 도로구간의 `ROAD_BT`(폭원)** | ✅ 실측값. 노량진동 54-8 → **25m 정확 일치** |

## 원천

**V-World 「도로명주소 도로구간」** — https://www.vworld.kr/dtmk/dtmk_ntads_s002.do?svcCde=MK&dsId=30055
`data/raw/(도로명주소)도로구간_서울/TL_SPRD_MANAGE.Seoul.shp` (EPSG:5179, 66,692건)

주요 속성: `ROAD_BT` 폭원(m) · `ROAD_LT` 연장(m) · `RN` 도로명 · `RN_CD` 도로명코드 · `ROA_CLS_SE` 도로구분

> 함께 받은 「연속수치지형도 도로중심선」(41.5만건)은 쓰지 않았다. 폭 관련 필드(`RVWD`)의 정의가
> 불명확하고, 도로명주소 쪽이 우리 `road_addr`와 도로명으로 직결돼 전면 판정이 정확하다.

## 파이프라인

```
build_road_width.py   shapefile(EPSG:5179) → WGS84 CSV   [build_all의 road_width 단계]
load_road_width.py    CSV → master.road_segment → master.building_road 산출
```

- `master.road_segment` — 도로 구간 66,691건(폭원·도로명·지오메트리, GIST 인덱스)
- `master.building_road` — 건물별 `front_m / side_m / rear_m / front_rn / n_roads`

## 전면 도로를 정하는 규칙

**추측하지 않는다.** `buildings.road_addr`의 도로명과 일치하는 구간이 곧 전면 도로다.
(`장승배기로 170` → 장승배기로 25m) 나머지 접한 도로는 폭 내림차순으로 측면·후면에 배정한다.

## 산출 결과 (2026-08-07, 서울)

- 건물 **511,255건**에 접도 폭 산출(30m 이내 도로 기준) · 평균 전면폭 **8.1m**
- 도로명주소로 전면이 **확정된 비율 96.4%**

| 검증 대상 | 전면 | 측면 | 후면 | 대장 분류 |
|---|---|---|---|---|
| 노량진동 54-8 | 장승배기로 **25m** | 4m | — | 광대세각 |
| 종로2가 71-6 | 종로 **35m** | 9m | 4m | 광대소각 |
| 역삼동 619-16 | 테헤란로1길 **8m** | 4m | — | 소로각지 |

세 건 모두 대장 분류 코드와 모순이 없다.

## 화면에서 쓰는 방식

매물상세 「토지정보」에 **실측 도로폭**(전면/측면/후면) 입력란이 있다.
표시 우선순위는 다른 값들과 같다 — **팀 수기 입력 > 배치 산출값 > 대장 분류 코드**.
브리핑 자료의 「도로상황」이 이 값을 그대로 쓴다.
