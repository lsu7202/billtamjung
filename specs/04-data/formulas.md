# 계산식 정의 (Formulas)

> **2026-09-06 · 매력도(F-16) 삭제.** 대표 결정 「아예 없앤다」. 아래 매력도·가치점수·등급(S~C)·8축 레이더 관련 서술은 역사 기록이며 화면·API·배치에서 전부 뺐다(0161). 적정가·수익률·활용유형·미래가치는 그대로.


> 파생 필드의 식·입력·예외를 못 박는 단일 출처. 필드는 `data-overview.md`, 식 ID는 `F-00`.
> **저장 정책**: 시계열에서 산출되는 대표지표(F-01·F-02·F-03)는 **매물 테이블에 비정규화 컬럼으로 캐싱**한다.
> 원천 시계열이 갱신되면 **재계산**한다. S01 필터 = 이 캐시값, S02 헤더 = 동일 값(검색↔상세 일치).

## 시계열 → 대표지표 (검색용 비정규화)

### F-01 실거래손익  *(실거래사례 시계열 → 스칼라)*
```
정의: 직전 실거래 → 최근 실거래 손익률
F-01 = (최근 실거래가 − 직전 실거래가) / 직전 실거래가 × 100   (단위 %, 소수점 2자리)
예외: 실거래 < 2건 → NULL (S01 필터 제외, S02 표시 '—')
```

### F-02 공시지가 상승률  *(공시지가 시계열 → 스칼라, 5년·10년)*
```
F-02a 상승률(5년)  = (현재 공시지가 − 5년전 공시지가)  / 5년전 공시지가  × 100
F-02b 상승률(10년) = (현재 공시지가 − 10년전 공시지가) / 10년전 공시지가 × 100
단위 %, 소수점 2자리. 해당 연도 데이터 없으면 NULL.
```

### F-03 광고 상승률  *(네이버광고 시계열 → 스칼라)*
```
정의: 직전 광고가 대비 최신 광고가 상승률
F-03 = (최신 광고가 − 직전 광고가) / 직전 광고가 × 100   (단위 %, 소수점 2자리)
예외: 광고 < 2건 → NULL
```

```
F-04 = Σ(필지별 공시지가 × 필지별 토지면적)        (단위 원)

  · 단일 필지 → 공시지가 × 대지면적 (기존식과 동일)
  · 다필지   → 필지마다 공시지가가 다를 수 있으므로 필지별로 곱해 합산
  ★ 대표필지 단가 × 전체 대지면적으로 계산하지 말 것.
    (buildings.공시지가_최신 = 대표필지 값 / 대지면적 = 전체 필지 면적 합 → 단위 불일치)

입력: parcels[공시지가_최신, 토지면적] + annex(건물↔필지 링크)

근거 (강남 실측 2026-07-19):
  다필지 2,521동 중 필지별 공시지가가 서로 다른 건물 220동.
  필지 데이터 완전한 1,909동 기준 → 오차 10% 초과 21동(1.1%), 중앙값 0.00%, 평균 0.45%.
  최대 사례: 논현동 60(4필지) +84.8% · 대치동 913-22(2필지) −56.7% · 도곡동 946-11(3필지) −55.0%.
  ※ 단가가 전부 같으면 기존식과 수학적으로 동일 → 오차는 '단가 상이' 시에만 발생.
     면적이 제각각인 것 자체는 오차 원인이 아니다(대지면적이 이미 전체 합).

#### 현재 건폐율·용적률의 출처  *(2026-08-30 재확정 · 0144)*

**화면에 서는 건폐율·용적률은 건축물대장 값 하나뿐이다.** 계산해서 채울 수 있어도 채우지 않는다 —
이 값이 계약서·중개대상물 확인설명서·브리핑 자료로 그대로 이어지고, 거기서 대장과 어긋나면
우리 잘못이 되기 때문이다. 대장이 비운 칸은 화면에서도 빈칸이다.

계산값은 **검색·분석 전용 표**(`master.building_calc`)에 따로 산다. 화면에는 절대 안 나간다.

| 어디 | 컬럼 | 무엇 | 쓰는 곳 |
|---|---|---|---|
| `master.buildings` | `bcr` · `far` | 대장 값 **그대로**(0이면 NULL) | 화면 · 보고서 · 계약서 · 브리핑 |
| `master.building_calc` | `bcr_calc` · `far_calc` | 필지 단위 계산값 | 검색 필터 · 여유율 · 활용 유형 |
| `master.building_calc` | `build_area_calc` · `far_area_calc` | 단독 필지에서 대지면적 × 대장 비율 | 검색 필터 |

계산 산식 — **용적률·건폐율은 건물이 아니라 필지의 값**이다. 대장은 그 필지의 값을 각 동에 똑같이 적는다.

| `far_src`/`bcr_src` | 산식 | 검증 |
|---|---|---|
| `parcel_copy` | 같은 필지 다른 동의 **대장 값**을 그대로 옮김 | 계산이 아님 |
| `computed` | 필지의 면적 합 ÷ 대지면적 | 대장에 값이 있는 427,107 필지 대조 → 99.1% 일치 |

  관악구 남현동 1136번지(12동): 한 동만 보면 0.43%, 12동 합치면 205.95% = 대장 값

- 커버리지: 용적률 화면 63.5% → 검색 83.9% · 건폐율 화면 63.3% → 검색 80.4%.
- 여유 건폐율·용적률(F-09)은 **분석값**이라 계산값 위에서 잰다. 대장 전사가 아니라 계약서로 안 간다.
- 대장이 0인 이유는 두 갈래다: **부속건축물**(원래 안 적는 것) · **전산화 이전 건물**(승인일도 없음, 42.6%).
  원본에 빈칸은 하나도 없다 — 전부 명시적 `0`이다. 그래서 이건 누락이 아니라 대장의 규칙이다.
- 자리: 계산 = `scripts/build_building_calc.py`(파이프라인 ②단계, 점수보다 먼저) ·
  필터 = `backend/app/domains/search.py` 의 `COALESCE(대장, 계산)`.

> **폐기된 옛 규칙** *(2026-08-10 · 0040·0041·0043·0044·0135)*
> 빌더가 대장 빈칸을 건축면적÷대지면적(건폐율 79,223동)·용적산정연면적÷대지면적(용적률 99,385동)으로
> 채워 `master.buildings` 에 실었고, 뷰가 역산을 한 겹 더 얹었다(건폐율 2,397 · 용적률 191 ·
> 건축면적 74 · 용적산정연면적 25,362). 산식 자체는 맞았지만 **계산값이 대장값 행세를 하는 게** 문제였다.

## 공실 파생

### F-13 총공실  *(enum: 있음 / 없음 / 미지정)*  *(호실 단위 재정의 2026-07-19)*
```
'공실'의 단위 = 호실. (층 단위 아님 — 한 층에 여러 호실이 있고 일부만 공실일 수 있다)
전제: 공실 호실은 보증금·임대료·관리비가 모두 0이다.

호실별 '공실상태'(공실 / 임대중 / 미지정) 우선순위 집계:
1) 호실 중 '공실'이 1건 이상 → 있음
2) 아니고 '미지정'이 1건 이상 → 미지정
3) 전부 '임대중' → 없음
예: (없음·미지정)→미지정, (있음·미지정)→있음
근거: 공실 여부를 모르는 경우가 많아 3값. 수익률(공실제외)(F-14) 트리거.
```

### F-14 수익률(공실제외)  *(호실 단위 재정의 2026-07-19)*
```
공실 호실을 분자·분모에서 모두 제외 → "임대된 부분만의 실질 수익률".
F-14 = (임대중 호실 총임대료 × 12) ÷ (매매가 × 임대중호실 면적비중) × 100
     · 임대중호실 면적비중 = 임대중 호실 계약면적 합 ÷ 전체 계약면적 합
     · 관리비 차감 안 함
참고: 공실 호실은 임대료가 0이므로 분자에서는 자동 제외된다.
      F-14의 실질 조정은 분모(면적비중)에서 일어난다.
관련: 총공실(F-13)='있음'일 때 일반 수익률과 차이 발생.
```

## 금액정보 산출 (층별 임대정보 → 자동 파생)  *(관리비 차감 안 함 · 확정 2026-07-18)*
```
입력: 호실별 [보증금, 임대료, 관리비, 공실상태, 계약면적], 매매가, 자기자본, 대출이자
출력: 총공실, 총보증금, 총임대료, 총관리비, 수익률(만실), 수익률(공실제외), 자기자본수익률

집계 규칙 (2026-07-19 확정):
  총보증금·총임대료·총관리비 = 전 호실 단순 합산.
  공실 호실은 세 값이 모두 0이므로 별도의 공실 제외 처리가 필요 없다.
  → 세 항목의 공실 처리 규칙이 서로 달라지는 문제가 구조적으로 발생하지 않는다.

F-10 수익률(만실) (관리비 차감 안 함):
  만실 = 만실 총임대료(전 호실 임대 가정) × 12 ÷ 매매가 × 100
  ※ 기본 "수익률"=만실. 실질(공실 반영)은 F-14 수익률(공실제외)가 담당.
    별도 "현재 수익률"(현재임대료÷매매가)은 만실과 통합해 폐기(2026-07-23).
    단 F-11 입력의 "현재 총임대료"(실제 집계값)는 유지.
F-11 자기자본수익률 = (현재 총임대료 − 대출이자) × 12 ÷ 자기자본 × 100   (관리비 차감 안 함)

F-11b 취득 부대비용·총투자비·대출액  (추가 2026-08-09 · 현장 요구)
  취득 부대비용 = 매매가 × 부대비용률
    부대비용률 기본 5.7% = 중개보수 0.9 + 취득세등 4.6 + 법무사 0.2
    (상업용 일반 거래 기준. 개별 협의로 달라져 화면에서 수정 가능)
  총투자비   = 매매가 + 취득 부대비용
  대출액     = max(0, 총투자비 − 자기자본)
    ※ 실제로 손에서 나가는 돈은 매매가가 아니라 총투자비다.
      매매가만 보면 부대비용만큼 대출을 과소평가한다.
  LTV        = 대출액 ÷ **매매가** × 100
    ※ 담보가치 기준이 표준. 총투자비로 나누면 은행이 말하는 LTV와 달라진다.
```

### F-22 매도 가능성 (propensity to sell)  *(신규 · 2026-08-09 · S04 영업)*
> **★ 매물 축이 아니라 사람 축.** "이 건물이 얼마인가"가 아니라 "이 소유주가 지금 팔 만한가"를 본다.
> 벤치마크 = Reonomy propensity to sell. 다만 **부채·저당 데이터가 우리에겐 없다** — 다섯 축만 쓴다.
> **예측이 아니라 신호다.** 검증에 필요한 "그래서 팔았는가"는 실거래가 쌓여야 가능(수개월).
> 그때까지 총점 옆에 **축을 펴서** 보여준다 — 총점만 두면 아무도 안 믿고, 믿으면 더 위험하다.
```
sell_score = Σ 축점수 (합 100)

① 보유기간  30점 = min(마지막 거래 이후 연수 / 20, 1) × 30
   · 거래 이력이 없으면 **0점**(축 자체를 비운다). "오래 보유"로 간주하지 않는다 —
     서울 전체에서 거래 이력이 있는 건물은 소수라, 없음을 신호로 쓰면 전부가 후보가 된다.
② 노후도    25점 = min(max(연식 − 10, 0) / 40, 1) × 25      (10년부터 오르고 50년 만점)
③ 지가상승  20점 = min(max(공시 5년 변동률, 0) / 50, 1) × 20  (+50%/5년 만점 · 차익 실현 유인)
④ 개발여지  15점 = min(max(법정 − 현재 용적률, 0) / 200, 1) × 15  (%p · F-09b와 같은 어법)
⑤ 정비구역  10점 = 정비구역 편입 시 고정 10점(master.building_redevel)
```

## F-24 임대료·보증금 추정 — 공시지가 주축(v4) *(2026-08-30)*

**정본 코드**: `scripts/rent_estimate/rent_common.py` · 적재 `build_floor.py` / `build_bldg.py`
**계수**: `scripts/rent_estimate/_rent_v4_coef.json` (굽는 도구 `fit_rent_v4.py`)

### v4 — 자리를 공시지가에 맡긴다

부동산원 상권 요율은 서울을 68칸으로만 나눈다. 같은 상권 안에서 어느 자리인지를 못 본다.
공시지가는 **필지마다** 다르다. 그래서 자리 잡는 일은 공시지가에 맡기고,
상권 요율은 「이 동네 임대료 수준」을 잡는 데만 쓴다.

```
층 단가(원/㎡ 임대가능면적/월)
  = K × a[층대] × 공시지가 ^ b[층대]
    × clamp(상권요율 상대값 ÷ 0.861, 0.5, 2.0) ^ 0.4
    × (1 − 0.06) ^ min(연식 ÷ 10, 4)
    × clamp(역거리 ÷ 400, 0.5, 2.0) ^ (−0.05)
```

층대별 지수 b 는 0.44~0.53 — 임대료는 공시지가의 대략 제곱근으로 움직인다.
공시지가가 없는 건물은 **v3(상권 요율)로 돌아간다.** 조용히 틀린 값을 내지 않는다.

**지하3 이하는 × 0.72.** 층대 `B` 는 지하를 한 칸으로 묶는데 깊이가 내려가면 실제로 싸진다.
크롤 잣대에 건물·층까지 맞춰 재보니 지하1 0.95 · 지하2 0.99 인데 **지하3 이하만 1.21** 로
다른 층(전체 0.86)보다 40% 높게 서 있었다. 0.862 ÷ 1.205 = 0.72.
지하4·5 는 실측이 더 낮지만(0.54·0.63) 표본이 110·23건뿐이라 더 쪼개지 않는다.

구를 갈라 학습·검증한 실측(`experiment_rent_v3.py`, 검증 12구 2.9만 층):

| | 절반이 이 안에 | ±20% | ±30% |
|---|---:|---:|---:|
| v3 상권 요율만 | 32.9% | 31.5% | 46.1% |
| **v4 공시지가 주축** | **28.2%** | 36.6% | 52.5% |

### 눈금은 v3 을 잇는다

크롤은 **호가**고 부동산원 표는 **실계약**이다. 크롤 중앙에 맞추면 전 서울 임대추정이
한꺼번에 19% 올라간다 — 호가를 계약가로 내미는 셈이다.
그래서 K 는 **v3 의 중앙값을 그대로 잇게** 잡았다(K = 1.0006).
흩어짐만 줄이고 레벨은 건드리지 않는다. 호가 대비 중앙 0.838 → 0.857.

### 크롤은 계수를 굽는 자리에만 있다

a·b·rmed·K 는 크롤 잣대로 **한 번** 굽고 JSON 에 박는다. 파이프라인은 다시 굽지 않는다.
매번 다시 구우면 남의 사이트를 긁어야 파이프라인이 도는 꼴이 된다.
**예측 입력은 공시지가·상권요율·연식·역거리뿐이다** — 층별 호가보정 상수(FLOOR_ADJ)와 같은 성격이다.

### (v3 이력 — 아래는 v4 가 얹힌 골격)

### 무엇이 문제였나

임대 요율은 한국부동산원 통계표에서 온다. 그런데 그 표는 **상권 하나에 요율 하나**다.
같은 상권 안의 대로변과 뒷골목이 똑같이 매겨진다.

보증금은 더했다 — 월세 × 상수 하나가 서울 전역·모든 층에 붙었다.
크롤 실측 중앙값이라 레벨은 맞지만, 동네마다 다른 보증금 관행을 통째로 뭉갠다.

### 유동인구는 총량이 아니라 주야비다

실거래 평당가로 쟀다(7,204건, 스피어만 순위상관 · `experiment_pop_rent.py`).
임대 실측(`app.floor_rents`)이 세 줄뿐이라 직접 못 재고, 추정이 옳다면
추정이 높은 건물이 실제로 비싸게 팔려야 한다는 것을 잣대로 삼았다.

| 산식 | 스피어만 |
|---|---|
| 지금 (상권 요율만) | 0.4595 |
| + 유동인구 총량 (√) | **0.3034** ← 나빠진다 |
| + 주야비 (낮÷밤) | **0.5739** ← +11.5p |

총량이 안 되는 이유는 그것이 상업 가치가 아니라 **주거 밀도**를 재기 때문이다 —
밤 인구는 평당가와 오히려 음의 상관(−0.18)이다. 사람이 많이 사는 동네일수록 상가가 싸다.
반면 낮÷밤은 「이 자리가 얼마나 상업지인가」를 잰다.

```
pop_adj = clamp(낮인구 ÷ 밤인구, 0.6, 2.0) ^ 0.5
```

클램프·지수는 격자탐색에서 골랐다(전체 +11.5p · 같은 상권 안에서도 +4.0p).
생활인구가 없는 건물(격자 미매칭)은 1.0 — 예전 산식 그대로다.

### 보증금 배율은 상권 전환율을 따른다

통계표의 **전환율**(시트 113/207/307)이 상권별 차이를 실측으로 준다.
전환율은 보증금 1원을 월세로 환산하는 연이율이라, 낮은 동네일수록 같은 월세를 만드는 데
보증금이 더 든다.

```
보증금배율 = 13.0 × (서울평균 전환율 ÷ 이 상권 전환율)     [8.0 ~ 20.0 로 가둠]
```

전월세전환율과 월세보증금비율은 다른 개념이라 **절대값은 못 쓰지만 상권 사이의 비는 쓸 수 있다.**
레벨은 크롤 실측(13.0 · 2026-08-30 재측정, 25.7만 매물)이 잡고 결이 전환율을 따른다.
실적재 결과 **10.9 ~ 16.2**(평균 12.79)로 갈린다.

**층별로는 나누지 않는다** — 통계표에 층별 전환율이 없다.
1층 상가와 사무실의 관행이 다른 건 알지만, 근거 없이 숫자를 지어내면
그게 틀렸을 때 아무도 못 잡는다.

### 통계표 파일은 이름으로 찾지 않는다

`STAT_FILE` 에 파일명을 박아 뒀더니 크롤러가 다음 분기를 받아온 순간 빌더가 죽었다 —
「2026년 1분기 …」를 찾는데 받은 건 「26년 2분기 …(공표용)」이었다.
분기 표기가 해마다 바뀌므로 이름을 맞히려 하지 말고 **파일 수정시각이 가장 새 것**을 쓴다.
