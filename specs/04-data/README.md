# 04-data 문서 역할 지도

> 데이터 문서가 겹치지 않도록 각 문서의 **단일 책임**을 정의. 2026-07-14.
> 필드가 바뀌면 **해당 책임 문서 한 곳만** 고친다.

## 4개 층

| 층 | 질문 | 문서 | 단일 책임 |
|---|---|---|---|
| **① 원천·조인** | 원본이 뭐고 어떻게 붙나 | `mart-layout.md` | 건축HUB 마트 컬럼 위치(역공학) |
| | | `codes-vworld.md` | V-World/국토부 코드 정본(지목·용도지역·이용상황 등) |
| | | `data-relations.md` | 원본↔통합 키·조인 관계(실증 검증) |
| **② 필드 마스터** | 어떤 필드가 **있나** | `data-overview.md`(컬럼정의서) | **전체 필드 카탈로그** — 의미·수집방식·원본·허용값·상태 |
| | | `data-dictionary.md` | 필드 단위·정밀도·예시·검색타입(②의 상세편) |
| **③ 값·식 규칙** | 값이 어떻게 정해지나 | `formulas.md` | 파생 필드 계산식 |
| | | `enums.md` | UI 드롭다운/상태값 value 목록(수기 필드) |
| **④ 구현·화면** | 어떻게 저장/표시하나 | `schema.md` | **DB/CSV 물리 레이아웃**(테이블·컬럼·타입·JSON) |
| | | `field-inventory.md` | 화면 ↔ 필드 매핑 |

## 핵심 원칙

1. **필드 마스터는 `data-overview`(컬럼정의서) 하나.** "무슨 필드가 있나"의 단일 출처. 각 필드에 **수집방식(공공/파생/수기)** 표시.
2. **`schema`는 컬럼정의서의 모든 필드를 DB 물리 구조로 표현.** ← 수기 필드도 포함(앱이 생기면 매매가·CRM도 저장되므로). 지금 강남 샘플엔 수기 입력값이 없어 비어있을 뿐, **수집방식으로 자르지 않는다.**
   - 컬럼정의서 = "무엇이 있나(의미)" · schema = "어떻게 저장되나(물리)" — 둘 다 전체 필드를 다루되 관점이 다름.
3. **허용값(코드)은 원천에만.** 코드 정본=`codes-vworld`, UI value=`enums`. 컬럼정의서는 "이 필드는 어느 코드집 사용"만 참조.

## 관계 요약

```
① 원천·조인  →  ② 필드 마스터(컬럼정의서)  →  ④ schema(물리) · field-inventory(화면)
                        ↑ ③ formulas·enums(값 규칙)
```

- 원천(①)에서 뽑은 걸 컬럼정의서(②)가 필드로 정의하고, 그걸 schema(④)가 DB 구조로 구현, 화면(field-inventory)에 매핑.
- 컬럼정의서 ⊇ schema가 아니라 **동일 필드집합, 관점만 다름**(의미 vs 물리).
