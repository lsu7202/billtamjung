# 개발자 지원 문서

지원처 정본 = 채용 공고 원문. 작업 폴더 = `docs/지원/<회사>/`.
결(結)은 사업계획서 스킬(`bizplan`)과 같다. 다른 점은 독자다. 심사위원이 아니라 **같은 직군 개발자**가 읽는다.

## 0. 먼저 지킬 것

1. **없는 경험을 만들지 않는다.** 안 해 본 것은 안 썼다고 쓴다. 사전과제와 인터뷰에서 그대로 물어본다.
   모노레포·MFA처럼 공고가 원하지만 내가 안 해 본 것은 **「관심」이 아니라 「가장 가까운 경험」**으로 답한다.
2. **수치는 잰 것만.** 잰 방법을 한 줄로 같이 쓴다(무엇을, 어떤 환경에서, 몇 번). 못 재면 숫자를 빼고 현상을 쓴다.
3. **경험을 나열하지 않는다.** 공고가 직접 말했다. 「임팩트와 러닝 포인트」다. 한 항목 = 문제 → 원인 → 조치 → 결과 → 배움.
4. **회사 업무와 잇는다.** 내 경험이 그 회사의 **어느 업무 축**에 붙는지 문서 안에서 말한다.
5. **대표가 준 문장은 그대로 쓴다.** 고칠 수 있는 것은 오탈자와 띄어쓰기, 기술 용어의 정식 표기뿐이다.

## 1. 공고 분해법

공고를 세 벌로 나눈다. 이 셋이 문서의 목차를 정한다.

| 갈래 | 뽑는 것 | 쓰는 곳 |
|---|---|---|
| **업무 축** | 「합류하면 함께할 업무」·「지금까지 이런 일을 했어요」 | 포트폴리오 목차. 내 경험을 이 축에 배치 |
| **평가 축** | 「이런 분과 함께하고 싶어요」 | 이력서 각 항목의 마무리 문장 |
| **증빙 요구** | 「이력서는 이렇게 작성하시는 걸 추천해요」 | 이력서에 반드시 답해야 하는 질문 목록 |

### 토스증권 프론트엔드 챕터 (2026.09 공고 기준)

**정체.** 제품 화면을 만드는 팀이 아니라 **FE 플랫폼·인프라 팀**이다.
「제품팀 개발자들이 성능 최적화를 쉽게 할 수 있도록 가이드와 모듈을 제공해요」가 핵심 문장이다.
따라서 「화면을 예쁘게 만들었다」는 통하지 않는다. **다른 개발자의 생산성과 서비스의 한계치**를 다뤘는지를 본다.

**업무 축 여섯.**

| 축 | 내용 | 규모 조건 |
|---|---|---|
| A 성능 | 브라우저·CDN·네트워크 전 구간 최적화 | 400만 DAU · 30만 동시 접속 |
| B 아키텍처 | 팀 간 독립 개발을 위한 자체 MFA 프레임워크 | 서비스 다수가 한 앱처럼 |
| C 배포 | AWS 기반 자체 배포 인프라와 파이프라인 | 하루 N번 배포 |
| D 관측 | 클라이언트 행동 로그, 실시간 모니터링·에러 대응 도구 | 실시간 트래픽 |
| E 웹뷰 | 네이티브 ↔ 웹뷰 전환의 연속성, 플랫폼 호환 문제 격리 | Android·iOS 양쪽 |
| F 테스트 | Storybook·Playwright 기반 테스트 환경 구축·운영 | 팀 전체가 씀 |

**평가 축 넷.**

1. **근본 원인.** 증상을 덮지 않고 원인을 짚었는가
2. **주도성.** 시키지 않은 문제를 찾아내 고쳤는가
3. **자동화.** 반복되는 운영 일을 없앴는가
4. **테스트.** 깨지는 것을 미리 잡는 장치를 두었는가

**이력서가 답해야 하는 질문 다섯.** 공고가 「있으면 알려 주세요」라고 적은 것은 전부 질문이다.

- 브라우저 동작 원리를 이해하고 성능을 올린 경험
- 트랜스파일링·번들링을 이해하고 브라우저 지원 범위를 다룬 경험
- 두 자릿수 패키지를 하나의 모노레포로 관리한 경험
- 새 기술을 찾아 도입한 경험
- 각 경험의 **임팩트와 러닝 포인트**

**스택.** React · TypeScript / PNPM · Yarn / ESBuild · Vite · Webpack · SWC · Babel /
AWS · CloudFlare · Terraform / Sentry · Grafana / GitHub Actions · GoCD.
내가 쓴 것과 안 쓴 것을 구분해 적는다. 안 쓴 것은 **비슷한 자리의 무엇을 썼는지**로 답한다.

## 2. 재료를 축에 붙이는 법

프로젝트를 통째로 설명하지 않는다. **문제 하나 = 항목 하나**로 쪼개고, 각 항목에 축 이름을 붙인다.
붙일 축이 없는 경험은 이력서에서 뺀다(포트폴리오 뒤쪽 「그 외」로 내린다).

    [축 A 성능] 검색 자동완성이 4.6초 걸렸다
      문제 : 입력할 때마다 화면이 멈춤
      원인 : (프로파일링으로 확인한 진짜 원인)
      조치 : (무엇을 바꿨는지, 왜 그 방법인지)
      결과 : 4.6s → 0.15s (무엇을 어떻게 쟀는지)
      배움 : (다음에 같은 문제를 만나면 무엇부터 보는가)

**항목 고르는 기준.** 축에 붙고, 원인이 분명하고, 결과를 잴 수 있는 것. 셋 중 하나라도 없으면 뒤로 뺀다.

## 3. 문서 골격

### 이력서 (A4 1~2장)

    이름 · 직무 한 줄 · 연락처 · GitHub · 포트폴리오 링크
    한 줄 요약        무엇을 만드는 사람인지 한 문장. 지원 직무의 낱말로
    핵심 역량 3~4     축 이름 + 근거 한 줄씩
    프로젝트          대표 프로젝트 하나를 깊게. 항목 4~6개(문제→원인→조치→결과→배움)
    기술              쓴 것 / 다뤄 본 것 두 칸으로 나눔. 한 줄에 나열하지 않음
    학력·수상         짧게

- 시간순 나열 금지. **축순**으로 배치한다.
- 한 항목은 3~5줄. 그 이상이면 포트폴리오로 내린다.
- 각 항목 끝에 평가 축 중 하나가 읽히게 쓴다(근본 원인·주도성·자동화·테스트).

### 포트폴리오 (웹 또는 PDF)

    표지        제품 한 장 소개 + 역할 + 기간 + 규모(유저·데이터)
    아키텍처    그림 하나. 내가 설계한 경계가 보이게
    문제 해결   축별로 2~4개. 이력서 항목의 확장판(코드·그래프·수치 포함)
    회고        무엇을 다시 한다면 어떻게 할 것인가

- **그림이 본문이다.** 글은 그림이 말하지 못하는 것만 쓴다.
- 코드는 **한 화면에 들어오는 만큼만**. 전후 비교가 목적이면 diff 로.
- 측정 화면(프로파일러·네트워크 탭·로그)은 캡처를 붙인다. 숫자만 쓴 것보다 강하다.

### GitHub

    프로필 README   무엇을 만드는 사람인지 3줄 + 대표 저장소 2~3개 + 연락처
    대표 저장소     README 가 곧 포트폴리오 요약본
      한 줄 소개 / 데모·스크린샷 / 문제와 해결 3~4개 / 아키텍처 그림 / 실행법 / 기술 선택 이유
    커밋            메시지가 곧 사고 과정이다. 「무엇을 왜 고쳤는지」가 보이게

- 저장소를 많이 두지 않는다. **대표 하나를 끝까지 다듬는다.**
- 비공개 저장소면 README 와 그림만 담은 공개 저장소를 따로 판다. 코드를 옮기지 않는다.
- 언어 통계·잔디는 꾸미지 않는다. 읽는 사람은 커밋 내용을 본다.

## 4. 한국어 작성 규칙

### 문장

- **경어체 평서문.** `~했습니다` `~입니다`. 사업계획서의 명사 종결(`~함`)을 쓰지 않는다.
- 한 문장 = 한 사실. 두 절 이상 이어 붙이지 않는다.
- **주어를 숨기지 않는다.** 내가 한 것과 팀이 한 것을 구분해 쓴다.
- 결과를 먼저, 과정을 뒤에. 「4.6초를 0.15초로 줄였습니다. 원인은 …였습니다.」
- 접속은 한자어로. 다만 · 반면 · 따라서 · 결국.

### 기술 용어

| 규칙 | 예 |
|---|---|
| 정식 표기를 쓴다 | 프론트엔드(프론트앤드 아님) · 백엔드 · 타입스크립트 · 웹뷰 |
| 영문 고유명사는 원문 그대로 | React · Vite · PostgreSQL · Cloud Run |
| 한글로 굳은 말은 한글로 | 번들링 · 트랜스파일링 · 캐싱 · 렌더링 |
| 약어는 처음 한 번만 풀어 쓴다 | MFA(Micro Frontend Architecture) |
| 섞어 쓰지 않는다 | 「DB 쿼리를 날렸습니다」 → 「DB에 질의했습니다」 |

### 쓰지 말 것

| 금지 | 왜 |
|---|---|
| 「열정을 가지고」 「최선을 다해」 | 아무 정보가 없다 |
| 「다양한」 「여러」 「등등」 | 몇 개인지 쓴다 |
| 「성능을 개선했습니다」만 쓰기 | 무엇을 얼마나 개선했는지가 없다 |
| 대시(—)를 연결어로 | 프로젝트 규칙. 쉼표와 마침표로 |
| 「~를 통해 ~를 함으로써」 | 영어 직역체. 어순을 다시 짠다 |
| 자기 비하(「미숙하지만」 「부족하지만」) | 판단은 읽는 사람이 한다 |
| 이모지 | 이력서·포트폴리오 본문에 쓰지 않는다 |

## 5. 만드는 법

작업 폴더에 이렇게 둔다. 굽는 방법은 `bizplan` 스킬과 같다.

    이력서.html / 이력서.pdf
    포트폴리오.html / 포트폴리오.pdf
    _doc.css          인쇄 스타일(A4 · 여백 · 표 · 불릿)
    _chart*.svg       아키텍처·성능 그림
    README.md         GitHub 대표 저장소용
    프로필.md          GitHub 프로필 README 용

PDF 굽기와 크롬이 매달릴 때의 처리는 `bizplan` 스킬 5절을 그대로 쓴다.

## 6. 내보내기 전 확인

- [ ] 각 항목에 축 이름이 붙어 있다
- [ ] 각 항목에 원인과 결과가 둘 다 있다
- [ ] 모든 수치에 잰 방법이 붙어 있다
- [ ] 안 해 본 것을 해 본 것처럼 쓴 문장이 없다
- [ ] 공고가 물은 다섯 질문에 전부 답했다(못 하는 답도 답이다)
- [ ] 이력서가 2장을 넘지 않는다
- [ ] GitHub 대표 저장소 README 가 이력서와 같은 사실을 말한다
- [ ] 회사 이름·직무명이 공고 표기와 같다(예: Frontend Developer)
